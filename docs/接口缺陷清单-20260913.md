## 一、P0：可复现的 500 / 静默改数据

### 1. `GET /api/bank` 超大 page → 500（SQLite int64 溢出）

```
GET /api/bank?page=9223372036854775807
-> 500 {"error":"internal error"}
```

服务端堆栈（uvicorn stderr）：

```
File "app/web/routes.py", line 1015, in bank_questions
    .offset((page - 1) * page_size)
OverflowError: Python int too large to convert to SQLite INTEGER
```

- 根因：`page` 只校验 `page >= 1`（`routes.py:944`），`(page-1)*page_size` 未限幅。
- 影响：任一已登录用户可稳定打 500；同时把内部堆栈刷进日志。

### 2. 超 int64 的整数参数 → 500（同类 9 个入口）

| 请求 | 结果 |
|---|---|
| `GET /api/questions/99999999999999999999` | 500 |
| `GET /api/questions/99999999999999999999/history` | 500 |
| `GET /api/questions/99999999999999999999/similar` | 500 |
| `GET /api/sessions/99999999999999999999` | 500 |
| `POST /api/favorites/99999999999999999999` | 500 |
| `GET /api/ugc/submissions/99999999999999999999` | 500 |
| `POST /api/admin/feedback/99999999999999999999/resolve` | 500 |
| `GET /api/review/suggestions?ids=99999999999999999999` | 500 |
| `GET /api/bank?page=1&page=99999999999999999999` | 500（重复参数，FastAPI 取最后一个） |

- 根因：路径参数注解为 `int`（Python 无上界）→ 直接进 SQLite 绑定，超出 int64 抛 `OverflowError`；
  全局 `unhandled_error_handler` 兜成 `{"error":"internal error"}`，日志留堆栈。
- 期望：统一 400（如 `Field(ge=1, le=2**31-1)` 或入口显式校验）。

### 3. `GET /api/today?date=9999-12-31` → 500（日期溢出）

```
GET /api/today?date=9999-12-31
-> 500 {"error":"internal error"}
```

```
File "app/web/routes.py", line 536, in today_questions
    end = start + timedelta(days=1)
OverflowError: date value out of range
```

- 附带解析不一致：`2026-09-13` 与 `2026-9-3` 都收（`strptime("%Y-%m-%d")` 容忍非补零），
  但 `2026-09-13 `（尾空格）400 —— 同一参数三种写法两种语义。
- 建议：改用 `date.fromisoformat` + 显式上界（如 ≤ 今天）。

### 4. `{"stem": null}` → 500，且**绕开全局异常处理器**

```
PUT /api/admin/questions/1981   {"stem": null}
-> 500，响应体为 Starlette 默认纯文本（content-type: text/plain）：
   "Internal Server Error"
   —— 不是 routes.py 里 {"detail": ...} / {"error": ...} 的 JSON 契约
```

服务端堆栈：

```
File "app/web/schemas.py", line 51, in _stem_strip
    v = v.strip()
AttributeError: 'NoneType' object has no attribute 'strip'
...
ERROR: Exception in ASGI application
```

- 根因：`AdminQuestionUpdate.stem: str | None = Field(default=None, min_length=6)` +
  `@field_validator("stem")` 直接 `v.strip()`。字段类型允许 `None`，validator 假设它是 `str`；
  `AttributeError` 不是 `ValidationError`，在依赖求解阶段抛出，**既不进 `RequestValidationError`
  处理器也不进 `Exception` 处理器**（handler 在 routing 内层）。
- 同样适用于任何 `str | None` + 无 `None` 保护的 validator 组合（`good_criteria`/`bad_criteria` 亦为可选类型）。
- 期望：400 + `{"detail": "..."}`（或把 validator 写成 `if v is None: return v`）。

### 5. `{"reviewed": null}` → 200，题目被静默下架

```
PUT /api/admin/questions/1981   {"reviewed": null}
-> 200 {"id":1981, ...}
DB: questions.reviewed_at = NULL          # 探针实测
```

- 根因：`routes.py:1309`

  ```python
  if "reviewed" in data:
      row.reviewed_at = datetime.now() if data["reviewed"] else None
  ```

  `data` 来自 `model_dump(exclude_unset=True)`，字段为 `bool | None`。
  显式传 `null` → falsy → 走 `else` 分支 → 下架。
- 影响：一个"空值语义"的请求把已发布题变成待审核题，普通用户立刻看不到（`/api/today`、
  `/api/bank`、`/api/review` 全部过滤 `reviewed_at IS NOT NULL`），无任何提示、无审计。
- 探针已还原该题（`reviewed_at = created_at`）。
- 期望：`"reviewed" in data and data["reviewed"] is not None` 才改；否则 400。

## 二、P1：正常使用会被破坏

### 6. `{"difficulty": null}` → 500，且同请求的其他字段已落库

```
PUT /api/admin/questions/1981  {"difficulty": null}
-> 500 {"error":"服务内部错误，请稍后重试"}

日志: NOT NULL constraint failed: questions.difficulty
      [SQL: UPDATE questions SET difficulty=? WHERE questions.id = ?] [parameters: (None, 1981)]
```

- `difficulty: int | None = Field(default=None, ge=1, le=5)`：`None` 是合法输入、非法数据。
- 更严重的是**先改后错**：同一请求若同时带 `{"stem": "...", "difficulty": null}`，
  `row.stem` 已赋值；`db.commit` 抛 `StorageError` 后 `get_session` 上下文回滚，
  但若同请求里含 `{"reviewed": null}`（见 #5）之类的路径，改动可先被提交 —— 局部更新
  不是原子的：要么整单成功，要么整单失败，现在的校验发生在 flush 阶段而不是入口。
- 建议：schema 去掉 `| None`（用 `exclude_unset` 表达"未提供"），或在路由里显式拒绝 `None`。

### 7. 被拒请求也消耗限流额度 → 合法请求被 429

干净重启服务后的实测（见 `_j_out.txt`）：

```
J1 第1次合法上传:                 200
J1 后续 11 次非法上传(后缀不允许): [400,400,400,400,429,429,429,429,429,429,429]
J1 第13次（合法）上传:            429  <- 被前面的非法请求吃光额度
J2 第1..11 次非法回答(过短):       [429 × 11]
J2 第12次（合法）回答:            429
```

- 根因：`write_rate_limit_middleware` 在进入路由**之前**调用 `_rl_allow(key, WRITE_LIMIT)` /
  `_rl_allow(key, LLM_COST_LIMIT)`，无论后续返回 200/400/403/404 都已计数。
- 叠加缺陷：`is_llm_cost` 分支是 `not _rl_allow(key, WRITE_LIMIT) or (is_llm_cost and not _rl_allow(key, LLM_COST_LIMIT))`
  —— 一次失败尝试可消耗两个桶的额度，且**没有"失败返还"**。
- 影响：一次批量上传（每次上传内部还会触发后台 LLM 质检/生成）就能把 `LLM_COST_LIMIT=10/分钟`
  用完；此后管理员的上传、`/api/daily/run`、用户答题全部 429，必须等 60 秒窗口滚出。
  正常 UI 操作被打断，且 429 文案（"操作过于频繁"）不提示还要等多久。

### 8. 验证码 60 秒限频实际上不生效（SMTP 失败路径）

```python
# app/email_code.py
def issue_code(email, send_fn=None):
    code = _new_code()
    send_fn(email, code)          # ← SMTP 未配置/失败时在这里抛 RuntimeError
    with _codes_lock:
        _codes[email] = {..., "last_sent": now}   # ← 限频依据，永远没写进去
```

- `can_send()` 读的是 `_codes[email]["last_sent"]`，而该字典只在 `send_fn` 成功后才写。
- 结论：只要 SMTP 报错（未配置 → 503；或网络/认证失败 → 500），`last_sent` 永远是 0，
  同一邮箱可无限次触发发送尝试。当前 `.env` 未配置 SMTP，所以线上表现为"503 无限重复"；
  一旦配上 SMTP 而密码过期，就变成"发信失败也能无限打"。60 秒限频名存实亡。
- 建议：把 `last_sent` 记在 `send_fn` 之前（先占位再发送，失败也保留冷却）。

## 三、P2：行为不正确/可被放大

### 12. 搜索关键词的 LIKE 通配符未转义

```
GET /api/bank?q=%   -> total=3009（全库）
GET /api/bank?q=_   -> total=3009（全库）
GET /api/bank?q=%%  -> total=3009
GET /api/bank?q=%25 -> total=14（URL 编码的 %，正常字面匹配）
```

- `routes.py:981-987` / `_tags_contains`（`routes.py:2642-2650`）直接拼 `ilike(f"%{keyword}%")`。
- 影响：`_` 与 `%` 是 LIKE 元字符，单字符输入即可绕过筛选条件并触发全表扫描
  （3009 行的 `stem ILIKE` + `EXISTS` 子查询），既是功能 bug 也是廉价放大点。

### 13. `/api/review/suggestions?ids=` 无数量上限

- `routes.py:1392`：`qids = [int(x) for x in ids.split(",") if x.strip().isdigit()]`，
  没有 `[:N]` 截断。实测 `ids=1..1999` 单请求返回 1999 条建议快照（200，约 100KB+）；
  3000 个 id 时被 uvicorn 的请求行长度上限挡下（`Invalid HTTP request received.`）。
- 期望：限制条数（如 100）并分页。

### 14. `stats` 的口径不一致（failed 判分）

```
/api/stats -> {"bank_total":3008,"answered_total":1,"done_questions":1,"avg_score":2, ...}
```

- `answered_total` 来自 `joined Judgment` 且 `Judgment.total_score IS NOT NULL`
  （`routes.py:880-894`），而 `done_questions` 来自 `_latest_judgment_by_question`
  （不过滤 failed）。判分失败的作答**记入"已完成题数"却不记入"已答数"**，
  打卡日历/趋势里当天 `answered=0`，与历史列表显示"已完成"自相矛盾。


- `_question_tag_map` 触发一次隐式重连。实测**未**造成连接泄漏
  （`pool.checkedout()` 退出前后均为 0，见 `_f_out.txt`），因为 `commit()` 已释放连接、
  后续读到的是 identity map 缓存值，所以返回的 `tags` 可能是**过期快照**。
- 属"能跑但脆弱"：一旦将来换成 `expire_on_commit=True` 或换连接池，这里会变成
  `ResourceClosedError` 或连接泄漏。建议缩进进 with 块。

### 16. `/api/import` 轮换后的 token 只回响应体

```python
new_token = create_token(imported_user.id)   # routes.py:1662
_set_auth_cookie(response, new_token)        # routes.py:1663
```

- 对比 `/api/auth/login`、`/api/auth/register` 都会 `_set_auth_cookie`；这里虽然有调用，
  但**同时把明文 token 放进 JSON 响应体**（`{"new_token": "..."}`），而其他入口刻意不返回明文
  （注释明确"HttpOnly Cookie，JS 不可读，降低 XSS 窃取面"）。契约不一致，且把 token 暴露给
  JS/日志/浏览器历史。实测：导入后旧 cookie 仍有效（备份库内 token 未变），`new_token` 冗余。

### 17. 直接上传模式的题干无长度上限 + 重复上传提示为 0

- `_insert_direct_questions`（`routes.py:2243-2248`）对题干不做长度校验，
  只做归一化哈希去重；`content` 上限 20MB → 单题题干可长达 20MB 落库，
  后续 `/api/bank`、`/api/questions/{id}`、判分 prompt 全量携带。
- 相同内容二次上传：`{"mode":"direct","count":0,"source_id":509}`（实测）——
  前端只能显示"导入 0 道题"，用户无法区分"内容重复"与"解析失败"。

### 18. 后台质检可删除已发布题；daily 部分失败无告警

- `_tag_direct_questions` 的 `verdict=delete` 分支（`routes.py:2348-2357`）会删除题目**及其全部
  会话/判分**（`for s in sessions: session.delete(s)`），不区分该题是否已 `reviewed`、
  是否已被用户作答。本次探针期间就观察到上传的题被后台质检直接删除。
- `task_logs` 里 4 次 daily 运行有 3 次 `partial`，错误均集中在大源生成：

  ```
  generate source#25: generation output must be a list, got dict
  generate source#83: question generation llm failure: cannot parse llm json output: Unterminated string ...
  ```
  即"分批生成防输出截断"在这些源上仍失败（同一源连续 3 次），而 `status=partial` 没有任何
  告警出口（无通知、无重试、无前端醒目提示），只能靠翻 `/api/daily/latest` 的 `error` 字段。

## 六、验证过的防护（无问题，供回归基线）

- 匿名访问全部业务/管理接口 → 401；伪造/过期/小写 `bearer` token → 401。
- 普通用户（role=user）访问 17 个 owner 专属入口 → 一致 403；`?reviewed=0` → 403。
- IDOR：他人 session / submission / 简历候选 token → 404（不泄露存在性）。
- CSRF：Cookie 写请求缺 `X-Requested-With: fetch` → 403；匿名写请求 → 401（未被吞成 403）。
- 注入：`category`/`sort`/`type`/`done`/`tag` 白名单校验 → 400；`batch-delete` 非整数/超 500 → 400；
  `review tag` SQL 注入串 → 400。LIKE 通配符除外（见 #12）。
- `/api/import`：非 base64 / 非 zip / 缺 `interview.db` / 非 SQLite / 缺用户表 / 成员 >100 /
  zip-slip 文件名 / 空 body → 全部 400；合法自备份导入 → 200 且题库可读。
- `answer` 长度 8000 通过 / 8001 → 400；空、纯空格、1 字符 → 400；`question_id≤0`、`kind` 非法 → 400。
- `/docs`、`/redoc`、`/openapi.json` → 404；`/static/../…`、URL 编码穿越 → 404。
- 并发收藏（幂等）/ 并发建会话（partial unique index 收敛为同一 session）/ 并发反馈（一致 409）均正确。
- 核心链路端到端：建会话 → 提交回答 → 轮询 `judging` → `done`，四维分值/总分/评语/参考答案/
  薄弱标签齐全（`_g_out.txt`；weighted total 2 = 0×0.3+0×0.3+10×0.2+0×0.2，合成正确）。
