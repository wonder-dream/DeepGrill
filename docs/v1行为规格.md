# v1 行为规格（v2 重写的输入）

> 用途：v2 的代码与架构从零重写，但**v1 用真实调试换来的行为契约不重写**。本文只记「v1 做过什么、为什么、v2 该不该保留」，不记实现方式。
> 证据：全部来自 `D:\document\InterviewAssistant` 逐行读取（`llm_client.py` / `dedup.py` / `quality.py` / `chain.py` / `judge.py` / `difficulty.py`）与 `docs/v1现状-20260913.md`。
> 结论标记：**继承** = v2 必须保留的契约；**重标定** = 结论本身依赖旧产品形态或旧语料，v2 必须重做实验；**废弃** = 随产品形态变化而失效。

---

## 1. LLM 调用层（全部**继承**）

这一层与产品形态无关，是纯粹的工程契约。

| # | 契约 | 为什么 |
|---|---|---|
| 1.1 | **屏蔽 SDK 内置重试**，只用本层重试 | v1 实测 SDK 重试与外层重试叠加，实际重试次数不可预测（`max_retries=0`） |
| 1.2 | 重试 **3 次尝试**，退避 **1s → 2s**（指数，`2**attempt`） | 够用且总等待可控 |
| 1.3 | 只对 **HTTP 5xx / 连接错误 / 超时**重试；**4xx 立即抛**不重试 | 4xx 是请求本身的问题，重试只是浪费配额与时间 |
| 1.4 | 默认 `max_tokens=8192` | 长 JSON 输出被截断会导致解析失败（v1 的实测结论） |
| 1.5 | 结构化输出用 `response_format={"type":"json_object"}` | 提高 JSON 遵从度 |
| 1.6 | **容忍 JSON 尾逗号**（`[1,2,]` / `{"a":1,}`），且容错**不得破坏字符串字面量内的逗号与转义引号** | v1 诊断出 9 个解析失败源，根因同一个 |
| 1.7 | 剥离 markdown 代码围栏后再解析（` ```json ` / ` ``` `） | LLM 常见的包裹行为 |
| 1.8 | 失败的**区分**：调用失败与 JSON 解析失败是两种错误，调用方据此选择不同降级 | 二者降级策略不同 |
| 1.9 | 所有失败必须**可降级为业务可继续**，不允许裸抛中断用户会话 | v1 的 15 处静默吞异常是反面教材：要降级，但**降级必须被记录**，不能静默 |

> ⚠️ **v2 必须修的反面模式**：v1 用 `except Exception` 吞掉异常后只写日志，导致「界面显示成功但数据没落库」「会话永远停在判分中」。v2 的降级必须**同时**产出：① 用户可见的状态 ② 可查询的失败记录。降级 ≠ 静默。

## 3. 追问策略（**结构性废弃，仅两条原则继承**）

v1 的 `CHAIN_PROMPT_V3` 是一套**按题目难度驱动**的深挖协议：目标深度 `min(5, difficulty+1)`、档位 `1-2→light / 3→medium / 4-5→deep`、轮数上限 `4/4/8/12/15`（再被 config 的 20 封顶）。**这套东西的前提是「刷题」——难度预设了该挖多深。** v2 的模拟面试里，追问由回答质量与能力边界驱动（ADR-0001），难度不再是靶子。

| # | 契约 | 状态 |
|---|---|---|
| 3.1 | 每轮除了生成追问，还要输出**两个质量维度**：`quality`（correct/partial/wrong/unsure）与 `completeness`（complete/partial/incomplete） | **继承** —— 这是 v2「探能力边界」的原料 |
| 3.2 | `level` 标注指**问题本身**所处深度，**与回答好坏无关**（答不出但问的是边界就是 L4） | 继承（语义定义清晰） |
| 3.3 | 五层深度阶梯的语义：**L1 概念 → L2 原理 → L3 权衡 → L4 边界/反例 → L5 横向联系** | 继承（作为深度评分的参照系） |
| 3.4 | **两次连续答差（wrong/unsure）→ 强制收尾**，防止在候选人明显不会的点上耗尽轮数 | **继承** —— 这是成本与体验的双重保护 |
| 3.5 | **轮数上限必须由外层强制**，不能只信 LLM 自觉 finish | **继承** —— 对 v2 的编排层（ADR-0001）同样成立 |
| 3.6 | 取「上一轮质量」必须在本轮持久化**之前**查询，否则读到本轮自己 | **继承** —— 这是个具体 bug，重写时极易再犯 |
| 3.7 | 单轮 LLM 失败重试 1 次；仍失败 → **降级为固定提示**（v1 用「请继续」）不中断会话 | 继承策略，**但提示文案必须重做**（面试官说「请继续」很出戏） |
| 3.8 | 目标深度由题目难度决定 | **废弃** |
| 3.9 | 浅挖档（难度 < 3）不传 `max_level`，避免「探到低层级 = 低分」惩罚低难度题 | **废弃**（连同其要解决的问题一起 —— v2 的深度评分不再来自预设层级） |
| 3.10 | `depth` 维度按「答到了预设的第几层」校准 | **废弃** —— 必须重新设计（ADR-0001 已记） |

| 4.2 | 总分合成：`accuracy×0.3 + completeness×0.3 + clarity×0.2 + depth×0.2`，四舍五入取整 | 继承（可重标定，但先别动） |

| 4.5 | 判分输出必须包含：四维分 + 评语 + 参考答案 + 薄弱主题 | 继承结构，**但薄弱点的表示要改**（见 5） |

## 5. 薄弱点与复习（**全部重做**）

v1：`judgments.weak_tags` 存字符串数组 → 聚合时拉全表回 Python 做 `Counter` → 复习列表按标签查同标签题。
问题：① 标签是判分 LLM 当场吐的，准确性无保障；② 「Java 并发 → Java」的子串映射是最脆的补救；③ 无层级，回答不了「该补哪个前置」。

v2：薄弱点 = **知识点 × 考察点** 的未命中记录（ADR-0002）。层级与前置依赖由知识地图提供。

| 保留的 | 说明 |
|---|---|
| 「低于某个总分门槛的题重新进入练习池」 | 思路继承，**门槛 70 需重标定** |
| 「未做过的题优先」 | 继承 |
| 复习讲义由 LLM 现生成 + 缓存 + 同 key 并发合并（防双份 LLM 调用） | 继承（v2 改为按需生成，见 CONTEXT.md 的分工） |

## 6. 难度分级（**继承定义，废弃其用途**）

`DIFFICULTY_SCALE_TEXT` 的五级定义（入门/基础/进阶/深度/专家，按广度/深度/权衡/经验依赖四维判定）写得很好，**继承作为标注标准**，用于生成与筛选。

但 v1 让难度**驱动追问策略**（目标深度、档位、轮数上限）—— 这部分在 v2 废弃。

## 9. 安全（**继承，v1 这部分做对了**）

| 项 | v1 做法 | v2 |
|---|---|---|
| 密码 | `scrypt`（n=2^14, r=8, p=1），`scrypt$salt$digest`，`hmac.compare_digest` 比对 | 继承 |
| 令牌 | 随机 32 字节；**库里只存 sha256**；有 TTL；可撤销；惰性清理过期行 | 继承 |
| Cookie | HttpOnly + SameSite=Lax + 可配置 Secure | 继承 |
| CSRF | 自定义头 `X-Requested-With`（跨站表单无法附加）+ SameSite 纵深 | 继承 |
| 限流 | 内存滑动窗口 + **reserve/settle**：4xx 释放额度，只有真正执行的请求计数 | **继承语义** —— 这个设计比"一律计数"正确得多 |
| XSS | 渲染 HTML 走白名单消毒；LIKE 元字符转义 | 继承 |
| 路径参数 | 整数路径参数统一范围校验（1..1e15） | 继承 |
| 生产硬化 | 未显式开启则禁用 API 文档端点 | 继承 |
| 传输层 | ❌ 无 TLS（已知缺口） | **v2 必须补** |

## 10. 三个必须避免的原样复制（v1 的失败模式）

1. **静默吞异常**（15 处）。降级可以，静默不行 —— 每次降级都要产出用户可见状态 + 可查询记录。
2. **进程内无界状态**（任务表 / 缓存 / 限流计数）。任何进内存的东西都要问：谁回收它？
3. **文档成为事实源**。v1 的测试数在文档里有 13 个不同取值、无一正确。v2 的事实源只能是代码与可执行检查。
