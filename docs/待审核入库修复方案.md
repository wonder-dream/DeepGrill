# 待审核入库修复方案（审核门禁失效三处问题）

> 结论：审核门禁代码已生效（待审核题进审核队列），但存在三处问题导致实际表现为「新题直接入库/题库数量直接增加」。

## 问题定位

### P0 — 回填迁移每次启动全量审批（app/db.py `_migrate_backfill_reviewed`）

```python
if "reviewed_at" not in cols:
    return   # 守卫写反：列不存在才返回
UPDATE questions SET reviewed_at = created_at
WHERE reviewed_at IS NULL ...   # 列存在 → 每次 init_db（每次服务启动）都执行
```

`reviewed_at` 列在绿地重建（8-11）就已存在 → 条件永远不成立 → **每次启动把所有待审核题批量置为已审核**。部署流程本身含 `up -d` 重启，等价于新题直接入库。原意是「门禁上线前存量题回填一次」，但无一次性标记，测试 `test_backfill_reviewed_migration` 还把错误行为固化成了断言。

### P1 — owner 普通题库页不过滤待审核题（直接原因）

- 后端 `app/web/routes.py:919`：owner 不带 `reviewed` 参数时**无任何过滤**（非 owner 才会强制看已审核）
- 前端 `app/web/static/app.js:311-328` `loadBank`：加载题库页不传 `reviewed`
- 效果：owner 点「立即更新」→ toast「Y 题待审核」→ 题库页「共 N 题」+Y 且列表直接显示新题 = 观察到的「直接入库」

`/api/stats`（侧边栏数字）已带 `reviewed_at IS NOT NULL` 过滤（routes.py:822），故只有题库页数字涨。

### P2 — 版本风险（已排除）

门禁代码全部为未提交工作区改动（16 文件 + 新文档），若从 git HEAD 部署则服务器无此功能。本次服务器为重新打包上传，已排除，但仍需提交入版本库。

## 修复方案

### Fix A（P0）`app/db.py` `_migrate_backfill_reviewed`

重写为带一次性标记 + 有证据跳过：

1. `PRAGMA user_version` 作迁移标记：`>=1` 直接跳过
2. 列缺失时 `ALTER TABLE questions ADD COLUMN reviewed_at DATETIME`（兜底老库）
3. 回填仅当**库内无任何已审核题**（`EXISTS(SELECT 1 FROM questions WHERE reviewed_at IS NOT NULL)` 为假）时执行——保护现存待审核队列：
   - 服务器（P0 已在部署重启时批过存量题，存在证据）→ 跳过回填 → 当前待审核队列原样保留
   - 本地 3009 存量全 NULL（无证据）→ 首次启动正常回填保持可见
   - 全新库无题 → 回填无害
4. 回填 + 置标记（`PRAGMA user_version = 1`）

测试 `test_backfill_reviewed_migration` 重写为三场景：
- 无证据（存量全 NULL）→ 回填一次且置标记
- 有证据（已存在已审核题）→ 待审核题保持 NULL，仅置标记
- 标记已置（user_version=1）→ 完全跳过

### Fix B（P1）`app/web/static/app.js` `loadBank`

恒传 `reviewed=1`：普通题库页只显示已审核题（owner/普通用户一致）。审核页 `reviewer.js` 独立传参（todo=0/done=1/all=不传），行为不受影响，「全部」tab 仍可看全部。

### Fix C（善后）`app/web/static/reviewer.js` 已审核 tab

新增「标记为待审核」按钮：调用 `PUT /api/admin/questions/{id}` body `{reviewed: false}`（后端 routes.py:1254 已支持，仅缺前端入口）。用于人工撤回被 P0 误批的题。

### Fix D（部署与文档）

1. 提交全部工作区改动后再打包（门禁代码目前未提交）
2. 《重新部署新版本.md》验证清单更新：
   - 题库页「共 N 题」不因立即更新增长；新题只出现在审核队列与审核页徽标
   - 部署后检查：审核队列中题数 = 立即更新生成数（P0 已修复，重启不再自动审批）
