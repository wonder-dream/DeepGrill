# 语音只做输入侧：候选人可以「说」，面试官只「写」

> 状态：accepted ｜ 影响文档：`docs/adr/0004-frontend-is-server-rendered.md`（面试页要处理的状态清单）· `docs/v2数据模型.md`（`attempts.input_mode` / `stt_text` / `clarity`）· `docs/v1行为规格.md` §4.1（继承 → 重标定）· `docs/v2范围基线.md` 决策 29–33 · `CONTEXT.md`（输入模态）

**候选人可以「说」，面试官只「写」。** 语音只做输入侧：面试页默认可语音回答、**可随时切回打字**；面试官的话仍是文字（SSE 流式）。三条连带规定：**转写不设「确认」环节**（直接进判分）、**不保存原始录音**（只存转写文本）、**保留口语特征**（但报告要标明本场是语音模式）。

## 为什么「输入侧做、输出侧不做」

成本几乎全在 TTS，不在 STT（单价与服务商见 `docs/v2范围基线.md`「已评估但暂缓」）：

```
语音输入（用户说 → 转写）    STT  8 分钟 ≈ 0.13 元/场        ← 便宜到可忽略
语音输出（面试官说 → 朗读）  TTS  3000 字 ≈ 0.24-1.50 元/场   ← 成本几乎全在这里
```

**语音输出把一场的成本乘以 10-30 倍**，而账号名额这个成本阀门是按文字算的 —— 「10-20 个名额」的预算容不下它。所以先把文字输出做出来，把「能不能做出来」的风险降回文字版。

**语音输入不受此限**：0.13 元/场（10 人 × 每日 1 场 ≈ 39 元/月）。换来的东西不小 —— 打字框允许反复修改措辞，而真实面试考的是**临场组织语言**；v1 的 `clarity` 维度在打字模式下测的是排版，不是表达。

## 转写为什么不设「确认」环节

**「先给用户确认/编辑再提交」曾是本项目的选择，后被推翻。**

要求确认等于把语音省下的打字成本又还回去 —— 它是**每轮都付**的固定成本，而识别错误是**偶发**、且下游模型本就能读通（"红黑树"被转写成"红黑书"，句子不成立，模型复述不出来）。判断候选人答得对不对、术语用没用对，本来就要读懂整段话。

## Considered Options

- **语音输出也做（TTS + 会动的头像）**：模拟面试的真实感最强。但成本是文字输出的 10-30 倍且几乎全在 TTS → **暂缓，不是否决**。形态判断仍然有效：若将来做，定为「音频 + 会动的头像」，**不做口型同步、不做数字人视频** —— 面试的紧张感来自"要说出口"，不来自"看得到嘴型"。
- **转写后让用户确认/编辑再提交**：曾是本项目的选择，理由是 STT 会认错技术术语。**推翻** —— 见上。
- **语音整个不做**：最省，但丢掉的正是真实面试的核心变量（临场组织语言），而它恰好是打字模式测不到的。
- **只做语音输出、不做输入**：方向反了 —— 贵的那一半留下、便宜且有价值的那一半丢掉。

## Consequences

- **面试页只需处理三个状态**：SSE 流式渲染、录音与转写、当前轮次状态。**没有「转写确认/编辑」这个中间态**（ADR-0004 的清单据此收窄）。
- **`attempts` 需要 `input_mode` 与 `stt_text` 两列**：前者记本轮是说的还是打的，后者存语音识别的**原始输出**（仅 `input_mode=voice` 时有值）。两列分开存是为了让「表达清晰度」有原始素材 —— 若只存一个，要么丢掉口语信号，要么让判分读不到实际提交的那份表述。
- **`clarity` 成为四维里唯一一个含义随输入模态变化的维度**：打字模式测组织与排版，语音模式测表达流畅、少口头禅。判分 prompt 必须按 `attempts.input_mode` 给不同的提示。**按 `docs/v1行为规格.md` 自己的分类法，v1 的「四维评分」因此不再是「继承」而是「重标定」** —— 它的维度定义依赖了 v2 才有的模态变量。
- **报告要标明本场是语音模式**：由 `attempts.input_mode` 派生（有语音轮即为语音场），**不新增字段** —— 存一个可从 `attempts` 推出的布尔量，只会多出一个可能与事实不一致的来源。
- **不保存原始录音**：录音是敏感数据且体积大，转写文本足够；报告标明模态，也是为了让读者不误判「表达清晰度」的来源。
- **STT 是一个新的外部依赖**：DeepSeek 没有语音能力，做语音输入就必须引入语音服务商 —— 这是本项目继 LLM 之后的第 2 个外部依赖。
- **网络路径是隐藏硬约束**（服务器在美东、用户在境内）：输入侧用户说完才上传，可接受；若将来做输出侧，语音是双向实时流，大概率需要**客户端直连语音服务**，详见 `docs/v2范围基线.md`「已评估但暂缓」的实施坑清单。
- **`docs/v2范围基线.md` 的「已评估但暂缓」一节保留为成本证据**（真实单价、并发、音色、流式支持）—— 决策与形态判断以本文为准。
