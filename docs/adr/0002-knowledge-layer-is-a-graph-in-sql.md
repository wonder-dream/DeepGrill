# 知识层用关系库里的图表示，不用图数据库，也不做页面互链

> 状态：accepted（⚠️ **部分被后续决策修正**：初稿写的是「岗位 → 知识领域 → 知识点」，决策 51/52 已改为「岗位是独立的一条轴，不在层级里」，且地图是森林 / DAG 而不是树；另被 ADR-0005 细化分层）｜ 影响文档：`docs/v2数据模型.md`（domains / knowledge_points / criteria / question_flags）· `docs/知识层构建管道.md` · `CONTEXT.md`（知识点 / 知识地图 / 考察点）

题库的知识结构用三张表 + 三类边表达：**知识领域 → 知识点** 的层级，以及「前置依赖 / 跨岗位复用 / 矛盾」三类边，题目通过外键挂在知识点上。**骨架由 LLM 从现有题目的题干与评分依据聚类而成，由人审核（通过 / 否决 / 合并）**；**题目挂载由 LLM 自动完成**，靠「用户实际答到了该知识点定义中的哪几条考察点」这一信号自动纠错。

## 三层结构，以及「合理」的判据

知识层是三层，**只有前两层需要人审**：

```
① 知识领域   「Java 并发」「RAG 检索」           人定 / 人审        几十个
② 知识点     「volatile」「内存屏障」             人审（关键）        几百个
③ 考察点     ① 保证可见性与有序性，不保证原子性   LLM 批量生成 + 抽查  上千条
             ② 底层靠内存屏障
```

**考察点不是知识点** —— 它是这个知识点的评分明细。把两者混淆会让人误以为要审上千个粒度判断，从而高估工作量。

判断一个知识点切得是否合理，用四条判据。它们**不是四个并列的检查项，而是一条决策流水线**，各管一层：

| 判据 | 管什么 | 层次 | 信号 | 动作 |
|---|---|---|---|---|
| **① 可判定** | 这个东西配不配当知识点 | 概念 · 人工 | 写不出「什么算答到、什么算没答到」的考察点 | **要么拆细，要么它根本不是知识点** |
| **② 复制传播** | 两个知识点该不该合并 | 结构 · 机器 | 一条考察点要被复制到多个知识点下才讲得通 | **合并**（候选建议，需人确认） |
| **③ 能力分离** | 一个知识点该不该拆 | 行为 · 数据 | 两个候选知识点经常「一个答对、一个答错」 | **保持拆开**；反之则合并 |
| **④ 稀有度** | 现在要不要建它 | 排期 · 机器 | 一个节点长期只挂 1-2 道题 | **先不建、挂父节点、等证据** |

### 判据 ① 的例外：有些东西真的不可判定，但真的该考

```
「有没有先问清需求边界」
「遇到不确定时有没有说"我不确定"而不是硬编」
「有没有主动量化（举例：说"耗时 100ms"而不是"很快"）」
```

这些是**行为特征** —— 面试官真正在意，但**无法逐条判定**。

处理方式**不是把它们改写成"可判定的样子"**（那是自欺），而是承认它并放到不同的位置：可以作为独立观察项由判分 LLM 自由评述，**但不进入考察点体系** —— 因为考察点的用途是「逐条判定 + 算命中率」，塞进去会污染统计。

### 判据 ② 的例外：通用表达类考察点可以合法地被引用多次

```
「先说结论再说理由」
  → 在「技术表达」下是考点 ✅
  → 在「系统设计」下也确实是考点 ✅
  → 这不是"两个知识点该合并"，而是"通用表达要求"
```

**因此判据 ② 只能产出「候选合并建议」，不能自动合并。** 区分办法是把**通用表达类**考察点显式标记为「共用考察点」，允许它被多个知识点引用。

### 判据 ③ 的局限（硬约束）

**它需要样本量。** 只有 20 个用户时，一个新知识点可能一个月只有几个人碰过 → 样本不够时**不要据此乱拆合并**。它只对高频知识点有效（恰好与判据 ④ 互补）。

**还有一处理论缺口**：若两个知识点**永远一起出现**（总在同一道题里问），就**从来没有"只考 A 不考 B"的样本** → 无数据 → 判据 ③ 沉默。这种情况只能靠判据 ① 加人的判断。

### 判据 ④ 的正确含义

**题少有三种完全不同的原因，不能一律当作"不该建"**：

| 题少的原因 | 正确处置 |
|---|---|
| 这个知识点真的不重要（没人考） | 确实不该建 |
| 它切得太细（粒度问题） | 挂到父节点 |
| 题本身有重复，5 道其实是一件事 | **先合并题** —— 这是内容问题，不是结构问题 |

所以判据 ④ 是**排期决策**（我没时间审），**不是质量判断**（这东西不成立）。「跟题库增长逐步细化」的准确含义就是这个。

## 粒度由题库决定，不由学科决定

没题的知识点是一整片永远空白的格子，不建。**因此「要建多少知识点」的答案来自题库，而不是来自某个技术领域的完整知识体系。**

实测 v1 的题目落在 1085 种标签组合上（题量见 `docs/v1现状-20260913.md`）。按题量分层决定人力的投入顺序 —— **前三行是「题量 ≥10 的组合」，共 15 + 28 = 43 种**：

| 分层 | 组合数 | 覆盖题目 | 处理 |
|---|---|---|---|
| ≥20 题 | 15 | 586 | **必须拆细** |
| 10-19 题 | 28 | 369 | 逐一看 |
| 5-9 题 | 102 | 650 | 抽审 |
| 3-4 题 | 106 | 361 | 抽审 |
| ≤2 题 | 834 | 1043 | **先不建独立节点**，挂到父节点 |

**人的投入集中在上表前两档的那 43 个组合上**（数据来源见上），其余跟着题库增长逐步细化。

**所以知识空间实际上很小。** 「要建上千个知识点」的担忧隐含了「要覆盖很多目标岗位」这个假设，但**现有题目绝大多数集中在同一个目标岗位**。需要认真切分的知识领域，光看题量只有十几个（Agent、系统设计、上下文工程、Prompt 工程、模型评估、Transformer/Attention、RLHF/微调、RAG/检索、推理优化、预训练、MLOps、Tool Use、Multi-Agent，加后端那零星几个）。

粗估：十几个领域 × 每个领域 10-30 个知识点 ≈ **几百个**，与前面的估计一致。

⚠️ **v1 的标签体系不可用作知识点的起点。** 标签是**主题维度**（"这道题涉及什么"），知识点是**能力维度**（"这道题考什么"）。实测证据 —— 题量最大的几个组合长这样：

```
 73 题  Agent
 72 题  Agent + 系统设计
 56 题  Agent + Prompt工程 + 上下文工程
 54 题  Agent + 上下文工程
```

这些不是可判定的知识单元。**所以必须逐题读题干与 `good/bad criteria` 来聚类，不能从标签聚合。**

## Considered Options

- **纯向量 RAG（v1 现状）**：切块 + 嵌入 + 相似度阈值。建造成本低，但「两道题是不是同一个东西」只能靠无语义的相似度猜，且 v1 实测最低相似度 0.5 仍拦不住语义兜底、真误命中约 20%。embedding 本身由 LLM 生成，其准确性同样无法保证。
- **LLM Wiki（编译成页面）**：每份资料编译成结构化页面并维护目录、交叉引用与矛盾记录。多个独立实践（[Obsidian Wiki 在 100 篇量级失效](https://dev.to/zaferdace/karpathys-obsidian-wiki-broke-at-100-articles-rag-fixed-it-4d4h)、[真实规模下的问题](https://dev.to/michaeltuszynski/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale-28jk)、[预注册对照实验](https://arxiv.org/html/2605.18490v2)）指向同一结论：它在几十页量级成立，规模一上来维护成本超过收益。而本项目是「三千道题 ÷ 一个人维护」，**页会腐烂，页面腐烂后下游全部跟着错**。
- **完整 Graph RAG（Neo4j + LLM 自由抽取实体与关系）**：最贵的是关系抽取，且抽取质量不可控、错误不可见。同时引入一个必须运维的中间件——本项目规模（几百个知识点节点）在内存里就是一个字典，用不上图数据库。

## Consequences

- **骨架错的代价远大于挂载错**：挂载错了只有一道题歪、且看得见；骨架错了整条链上所有题一起歪、且看不出来。因此**审核权必须留在人手上**，而 LLM 承担可批量、可自动校验的挂载工作。
- **判分读的是「一组知识点」，不是一个**：一道综合题牵动多个知识点（**决策 24** 已把关系改为多对多）。判分时取它牵动的**全部知识点的考察点**，而不是主知识点一处的定义。主知识点只负责「这道题住在哪」与挂载自修复的期望值。
- **「查表」指的是「查到该考什么」，不是「不需要 LLM 判断」**：判分仍然是 LLM 逐条判断"答到了哪几条考察点"。它消除的是「不知道该检查什么」这一类失败（v1 的检索误命中约 20%），而不是「判断本身」这一类失败 —— **后者的质量上限由考察点写得好不好决定**。
- **它替代的是 RAG 在「判分参照」上的用途，不是 RAG 的通用检索能力**：面对已归位的内容，判分依据确定、可追溯、能被答题数据纠错；面对**全新、无归属的内容**（例如让用户贴一段陌生技术文章来点评），没有知识点就没有考察点，这套东西给不出东西。向量召回仍保留在一处 —— **简历文本 → 相关知识点**，因为候选人的措辞无法预测。
- **矛盾记录是这套结构唯一白送的能力**：同一知识点下两道题口径不一致会被显式暴露，形成一个「题库哪里不干净」的仪表板。纯向量检索永远给不了这个。
- **去重不再需要标定相似度阈值**：重复的定义从「余弦超过某个数」变成「是否指向同一知识点」。v1 的 0.85 因此不是「重新标定」，而是**消失**。
- **运行时几乎不查图**：图是离线内容治理工具，不是运行时组件。
- **薄弱点的表示随之改变**：从判分 LLM 吐出的标签字符串（v1 靠「互为子串则映射」这种脆弱规则归一）改为「答不到哪个知识点的哪几条考察点」，天然带层级，因而能回答「该补哪个前置」。
