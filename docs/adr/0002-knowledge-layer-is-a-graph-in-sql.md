# 知识层用关系库里的图表示，不用图数据库，也不做页面互链

题库的知识结构用三张表 + 三类边表达：**岗位 → 知识领域 → 知识点** 的层级，以及「前置依赖 / 跨岗位复用 / 矛盾」三类边，题目通过外键挂在知识点上。**骨架由 LLM 从现有题目的标签分布反推成候选清单，由人审核（通过 / 否决 / 合并）**；**题目挂载由 LLM 自动完成**，靠「用户实际答到了该知识点定义中的哪几条考察点」这一信号自动纠错。

## Considered Options

- **纯向量 RAG（v1 现状）**：切块 + 嵌入 + 相似度阈值。建造成本低，但「两道题是不是同一个东西」只能靠无语义的相似度猜，且 v1 实测最低相似度 0.5 仍拦不住语义兜底、真误命中约 20%。embedding 本身由 LLM 生成，其准确性同样无法保证。
- **LLM Wiki（编译成页面）**：每份资料编译成结构化页面并维护目录、交叉引用与矛盾记录。多个独立实践（[Obsidian Wiki 在 100 篇量级失效](https://dev.to/zaferdace/karpathys-obsidian-wiki-broke-at-100-articles-rag-fixed-it-4d4h)、[真实规模下的问题](https://dev.to/michaeltuszynski/karpathys-llm-wiki-works-heres-what-broke-when-i-ran-it-at-real-scale-28jk)、[预注册对照实验](https://arxiv.org/html/2605.18490v2)）指向同一结论：它在几十页量级成立，规模一上来维护成本超过收益。而本项目是「三千道题 ÷ 一个人维护」，**页会腐烂，页面腐烂后下游全部跟着错**。
- **完整 Graph RAG（Neo4j + LLM 自由抽取实体与关系）**：最贵的是关系抽取，且抽取质量不可控、错误不可见。同时引入一个必须运维的中间件——本项目规模（几百个知识点节点）在内存里就是一个字典，用不上图数据库。

## Consequences

- **骨架错的代价远大于挂载错**：挂载错了只有一道题歪、且看得见；骨架错了整条链上所有题一起歪、且看不出来。因此**审核权必须留在人手上**，而 LLM 承担可批量、可自动校验的挂载工作。
- **矛盾记录是这套结构唯一白送的能力**：同一知识点下两道题口径不一致会被显式暴露，形成一个「题库哪里不干净」的仪表板。纯向量检索永远给不了这个。
- **去重不再需要标定相似度阈值**：重复的定义从「余弦超过某个数」变成「是否指向同一知识点」。v1 的 0.85 因此不是「重新标定」，而是**消失**。
- **运行时几乎不查图**：判分只读「这道题所属知识点的定义（考察点 / 不考察）」，是查表而非遍历。图是离线内容治理工具，不是运行时组件。向量召回只保留在一处——**简历文本 → 相关知识点**，因为候选人的措辞无法预测。
- **薄弱点的表示随之改变**：从判分 LLM 吐出的标签字符串（v1 靠「互为子串则映射」这种脆弱规则归一）改为「答不到哪个知识点的哪几条考察点」，天然带层级，因而能回答「该补哪个前置」。
