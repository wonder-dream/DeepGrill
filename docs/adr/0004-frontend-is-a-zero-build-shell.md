# 前端是零构建的薄壳，且不承载业务逻辑

前端使用原生 ES 模块 + JSDoc 类型注释，不引入打包器与框架。它的职责被限制为四件事：**表单、列表、流式文本显示、当前会话的轮次状态**。所有判断与业务规则留在 Python 侧。

前提是 owner 不编写也不调试前端代码（由 AI 生成）——因此选型标准不是「写得省力」，而是**出错时的排查面**。

## Considered Options

- **Vite + Vue / Svelte + TypeScript**：响应式天然适配对话界面，生态成熟。但多出「源码 → 构建 → 产物 → 浏览器」四层，构建配置本身即一类故障源；且需每年升级依赖，否则某天构建无声失败。
- **服务端渲染 HTML 片段 + 少量 JS**：最贴近 Python 开发者心智，但流式对话体验受损。

## Consequences

- **浏览器里的代码就是仓库里的代码**：改完刷新即生效，AI 与人都能直接对照，不存在看不见的产物层。
- **前端越薄，AI 生成代码的正确率越高**：不引入框架特有概念（响应式、生命周期、状态管理），生成与修复的上下文更小。
- **组件需手写**（弹窗、下拉、Toast 等）—— 但 v2 所需数量少于 v1 已手写过的规模。
- **过渡是可行的**：每个区块一个模块、渲染函数是纯函数（输入数据 → 输出 DOM，不读全局变量）。因此某个面板若日后复杂到难维护，可单独替换（如只给统计页引入 Preact），不必整体重写。「零构建」是可逆的。
- **UI 形态被限定为「单页状态机 + 对话框」**：若未来出现「多个面板互相触发刷新」的控制台型界面，本决定需要重新评估。
- **先做静态原型再接入逻辑**：视觉用无 JS 的静态页面确认，再接数据与交互。避免「一改样式就碰坏功能」。
- **不做组件库**：界面观感由设计令牌（间距尺度、颜色变量、字号比例、统一圆角与阴影）与状态细节（加载/悬停/聚焦/禁用/空态/错误态）决定，而非由框架决定。
