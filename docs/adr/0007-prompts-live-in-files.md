# Prompt 独立成文件，不写在代码里

所有 prompt 抽成独立文件（如 `prompts/cluster_candidates.md`），代码只负责**加载、填充变量、缓存**。改 prompt 是改一个 markdown 文件，不是改 Python。

依据：v1 的 prompt 硬编码在代码字符串里（`CHAIN_PROMPT_V3` 在 `chain.py` 第 23 行），靠一个版本号常量标记变更。结果是**改 prompt 要改代码、要跑测试、要重新部署** —— 而 prompt 恰恰是变更是常态的那部分。

## 为什么对本项目特别重要

**① 知识层构建要反复试错。** 聚类（3009 题 → 知识点清单）是可重跑的（成本几块钱、耗时 20-60 分钟），流程必然是「跑一遍 → 看质量 → 改 prompt → 再跑」。若 prompt 在代码里，每一轮试错都变成一次代码改动。

**② 改 prompt 这件事，owner 自己就能做。** 这符合本项目的实际分工：**prompt 是 owner 比 AI 更懂的部分**（他知道面试官该怎么问、什么算好的考察点），而代码不是。把 prompt 从代码里拿出来，等于把这块的控制权真正交回给 owner。

**③ 它让 prompt 可以像数据一样管理** —— 能 diff、能回滚、能并排对比两个版本的产出。

## Consequences

- **需要一套加载机制**：读文件 + 填充变量 + 缓存。比字符串常量麻烦，但只写一次。
- **prompt 与代码的对应关系变成隐式**：代码里只剩一个文件名。需要在 prompt 文件头部注明「谁在用它」，或反过来在调用处集中登记。
- **打包时必须确保 prompt 文件进镜像** —— 否则出现「本地能跑、线上找不到文件」。这是这类方案最典型的坑，要在 Dockerfile 与部署检查里各拦一次。
- **prompt 变更与代码变更可以分开提交**，因此 `docs/v1行为规格.md` §4.10 那条纪律（prompt 版本号显式标注、变更须同步测试与 fixture）需要重新表述：**版本化从「代码里的常量」变成「文件的 git 历史」**，而「变更须重测」这条纪律不变。
- **本决策覆盖全部 prompt**，包括本次讨论之外的（判分、追问、生成、质检）—— 一致的约定比逐个判断更省心。
