# 代码按领域切分，依赖方向单向，同时需要两个领域的动作归上层

一级目录**按领域切**（每个领域自含其路由、服务与逻辑），而不是按技术层（`routes/` `services/` `models/`）纵切。**领域之间互不 import**；当一个动作同时需要两个领域时，把它放到**能同时依赖两者的上一层**，而不是让两个领域互相 import。

依据：v1 的 `routes.py` 长到 3033 行、`create_app` 单函数 1751 行，**根因不是"没分层"，而是"所有领域住在同一个文件里"**。只把 `create_app` 拆成 `routes/interview.py` + `services/interview.py` 而领域仍横跨全局，长文件只是换了个名字。

## 依赖规则

```
接口层     web（服务端渲染页面 + 面试页 SSE）
                ↓
编排层     offline（聚类 / 挂载 / 生成 / 质检 / 自修复统计）
                ↓
领域层     interview   report
           bank        knowledge        profile   account
                ↓
基础设施   llm   db   config   errors   templates
```

**方向单向、禁止反向。** 尤其：

- **领域之间互不 import** —— `bank` 不认识 `knowledge`，`knowledge` 不认识 `bank`
- **基础设施不许 import 任何领域**（`llm` 里不许出现"题目"这个概念）
- 同一层内部只在明确许可时才依赖（`report` → `interview` 允许，因为报告是面试的产物）

## 那条规则的具体应用：挂载自修复住在 `offline`

挂载自修复需要同时碰「知识点的考察点命中统计」与「这道题挂在哪个知识点下」——**横跨两个领域**。它因此是这条规则最好的检验案例：

```
offline/self_repair.py       ← 只有它同时 import 两边
   ├─ knowledge.stats   →  取「这个知识点的考察点命中统计」
   └─ bank.questions    →  取「这道题」/ 标「挂载可疑」

bank 与 knowledge 互不 import
```

- `bank` **从不问**「我挂得对不对」——它只提供「给我一道题」与「标它可疑」
- `knowledge` **从不问**「哪道题挂错了」——它只提供「这个知识点的命中统计」

**写 `questions` 表的只有 `bank` 自己。** 这条保证的价值在于：以后想加一个「改题目」的功能时只有一条路可走，不会有人在最方便的地方直接写 SQL —— 而 v1 的 `routes.py` 里正是 64 处直接 `db.get_session()`、谁都能写任何表。

## 领域内部：标准三层，但业务层是函数

采用主流后端的三层骨架，**目录按领域切、分层靠文件名表达**：

```
<领域>/
  routes.py       ← 薄。只做参数校验、鉴权、调 service 或 pages、返回响应
  service.py      ← 业务规则与事务边界。**模块级函数，不是类**
  pages.py        ← 页面数据装配。**只调本领域的 service**（小领域可没有这个文件）
  repository.py   ← 数据访问的唯一入口
```

- **`db/models.py` 统一放全部表**（21 张）—— 不散落到各领域，因为表之间有外键关系，拆开会让关系断裂
- **`service.py` 里是函数，形态是 `def submit_answer(db, llm, session_id, text)`** —— `db` 当第一个参数显式传入。这与多数 Python 后端项目的真实写法一致（它们叫 Service 层，但写的是函数）
- **只在真正有状态的地方用类** —— 目前只有 `interview` 的编排（带循环的状态机，ADR-0001 已要求状态显式落库）

### 为什么需要 `pages.py`，以及为什么它不叫 `views.py`

**服务端渲染（ADR-0004）制造了这一层。** 前后端分离的项目没有它 —— 后端只出 JSON，数据怎么显示归前端管。一旦把呈现形状的责任搬回服务端，就必须有人负责「把数据整理成页面要的形状」。

而「渲染一个页面」所需的数据常常**横跨多个领域**（个人状态页要同时拿掌握度矩阵、额度余额、面试列表、前置缺口）。若把这段拼装放进 `routes.py`，路由层必然变厚 —— v1 的 `bank_questions`(124 行)、`import_backup`(113 行) 就是这么长出来的。

因此：

- **领域内的 `pages.py` 只能调本领域的 `service`**，它回答「本领域的数据该怎么呈现」（命中率怎么算、矩阵怎么排序）
- **跨领域的页面由 `web/` 层组合多个领域的装配函数** —— 与本文的依赖规则一致：跨领域动作放在能依赖两者的上层

**不叫 `views.py`**：在分层语境里 "view" 通常指控制器（Django 的 view 就是 controller），与这里的「装配」语义相反，未来读代码的人会误判。

**判据（区分 `pages.py` 与 `service.py`）**：*它影响数据内容，还是只影响数据形状？* 影响内容 → `service`；只影响形状 → `pages`。

**判据（用来判断某处该不该用类）**：*这个领域有没有跨调用存活的状态？*

```
account / bank / knowledge / profile   无状态 → 函数
interview                              状态跨轮次存活、要挂起恢复 → 类
```

这条判据自带纠错用途：若有人要给 `bank` 写一个类，问一句「它有跨调用存活的状态吗」—— 没有，说明设计走偏了。

### 为什么要有 `repository.py`

不是为了"以后可能换数据库"（单库单实现，那是没有收益的抽象），而是因为**它是一条硬规则的强制点**：

> **私有题集与公共题库同表，任何题目查询都必须过滤 `owner_user_id`；不允许业务代码直接 `select(Question)`**

把"所有题目查询"收进 `bank/repository.py`，外面只能调它 —— 这条规则就从「写在文档里靠自觉」变成「没有别的路可走」。

**同时配一条自动检查**：禁止领域层直接 import 全局 session（v1 有 64 处直接 `db.get_session()`，那是边界没开口子的结果）。

## Considered Options

- **按技术层纵切**（`routes/` `services/` `models/` `engine/`）：教科书式，但会长出一个巨大的 `services/interview.py` —— 只是把 3033 行的路由换成 2000 行的服务。
- **合并 `bank` 与 `knowledge` 为一个领域**：无循环依赖，代码最短。但「知识地图」与「题库」合起来会是最大的那个领域，而它们恰好是 v2 里最复杂的两个 —— 合并等于放弃分而治之。
- **允许 `knowledge` 直接写 `questions.primary_point_id`**：代码最短、没有"别扭感"。但 `knowledge` 因此必须知道 `questions` 表的结构；此后 `bank` 每改一个字段都要跨领域确认。**边界一旦开口，就不会只有一处。**

## Consequences

- **改动局部性最好**：改「追问收尾条件」时，相关代码（路由、服务、逻辑、测试）都在一个目录里。
- **单文件体积天然受限**：一个领域一个文件，而不是所有领域一个文件。
- **跨领域动作有一个固定去处**：放进能依赖两者的上一层（目前是 `offline`）。**这个模式会被反复用到**，不只是自修复。
- **`offline` 的职责比"管道"重**：它是编排层，不只是跑批。写自修复时会觉得"这明明是知识层的事却放在 offline" —— **这个别扭感是边界清晰的代价，不是设计失误。**
- **本决定没有涵盖"基础设施层的边界怎么划"**：例如模板渲染算基础设施还是 web 专属，待定。同层的许可依赖清单也待补全。
- 本文件记录的是**结构决策**；完整的领域与文件清单在实施时补全。
