# 离线任务是数据库里的任务表 + 独立 worker 进程，不用 Redis

> 状态：accepted ｜ 影响文档：`docs/v2数据模型.md`（jobs 表）· `docs/知识层构建管道.md`（用命令行而非队列）· `docs/v2范围基线.md` 决策 40-41

离线任务（聚类 / 挂载 / 生成 / 质检 / 自修复统计）落库成 `jobs` 表；**独立 worker 进程**轮询拉取执行。**同一份领域函数支持三种调用方式**：web 请求触发（提交后自动跑）、worker 轮询（定时 / 自动恢复）、命令行手动跑（一次性大任务，可 `--dry-run`）。

worker 与 web **共用同一个 Docker 镜像**，只是启动命令不同（`uvicorn …` vs `python -m app.offline.worker`）—— 因此不存在"两边代码不一致"这类问题，worker 直接调领域层的函数，与路由调的是同一批。

依据：v1 把离线塞进 web 进程（`BackgroundTasks` + 两处裸 `threading.Thread().start()`），结果是 8 处后台任务无并发上限、失败静默丢弃、`_process_ugc_submission` 崩溃后永久卡在 `processing`（没有 reaper）。

## 为什么不用 Redis + 队列

Redis + Celery/RQ 是标准答案，但它的收益与成本在本项目的约束下不成比例。

**收益里真正不可替代的只有两条**：跨进程即时通信（进度推送）、多机 worker。其余（削峰、横向扩展、任务优先级、成熟重试）在「20 个用户 + 单机 + 任务种类个位数」下都是边际的 —— 而任务状态落库后，"重试"就是一条 `UPDATE` 加一个计数器。

**代价里最要紧的一条是它拿走了事务性**：

```
数据库任务表：
    with db.transaction():
        db.add(interview)                  ← 业务写入
        db.add(Job(kind="compile", ...))   ← 投递
    # 同一个事务：要么都成，要么都不成

Redis 队列：
    db.commit()          ← 先写业务
    redis.enqueue(...)   ← 再投递
    # 中间崩了 → 业务写成功但任务永不执行；或反过来
```

**这恰好是 v1 那批"卡在中间态"的 bug 的根治办法**（v1 的 `_process_ugc_submission` 跨多次 session 与 commit、中间夹着 LLM 调用 —— 见 `docs/v1现状-20260913.md`），而 Redis 会把它堵死。

其余代价：多一个常驻进程（估算：空转几十 MB、实际约一百多 MB，而目标机器只有 2G）、多一块"要持久化要保活"的状态、调试路径变长（任务没跑要查三处而不是一条 SQL）。

**换回 Redis 的路很短**：`jobs` 表本身就是一个持久化队列，真需要多机时把"从表里拉任务"换成"从 Redis 拉"即可，任务函数不用改。

## 三个必须实现的机制

### ① 原子认领（防两个 worker 抢同一条）

不能"先查再改"，要靠一条 `UPDATE` 原子抢占：

```sql
UPDATE jobs SET status='running', worker_id=?, started_at=now()
 WHERE id = (SELECT id FROM jobs WHERE status='pending' ORDER BY id LIMIT 1)
   AND status='pending'          -- 关键：条件里再确认一次
RETURNING id
```

只有一个 worker 能让它影响 1 行，另一个影响 0 行（去抢下一条）。**这是数据库层面的事实，不靠代码自觉。**

### ② 心跳 + 超时回退（防卡死）

worker 每 30 秒 `UPDATE jobs SET heartbeat_at=now()`；回退逻辑把 `status='running' AND heartbeat_at < now() - 5min` 的记录放回 `pending` 重跑。

**v1 已有这个思路的雏形** —— 它给「判分中」的会话设了一个 600 秒的存活上限（视为进程已死，见 `docs/v1现状-20260913.md`），只是当时只用在判分上，没推广到后台任务。

### ③ 任务函数必须幂等

重跑是常态（超时回退、手动重跑），所以任务函数要写成"跑两遍结果一样"：

| 任务 | 重跑安全吗 | 为什么 |
|---|---|---|
| 聚类 / 生成 / 质检 / 挂载 / 自修复统计 | ✅ 安全 | 「读一批 → 算 → 写结果」，重算覆盖原结果 |
| 发通知 / 扣额度 | ❌ **不安全** | 重跑会发两次 / 扣两次 → 要么不进队列，要么加去重键 |

## Consequences

- **"worker 挂了怎么办"被简化成"重启它"** —— 状态在库里，不在内存里。
- **重试、进度查询、断点续跑、可观测全部免费获得** —— 它们都只是对 `jobs` 表的查询。
- **一次性大任务与线上服务物理隔离**：全库题目的聚类可以在 worker 里跑很久，web 不受影响；也可以用命令行跑并实时看点输出。
- **`jobs` 表需要有回收者** —— 已完成的记录要按 TTL 清理。这直接撞上 `AGENTS.md` §3.2「任何进内存/新增的状态都要有回收者」：这里换成了"谁清理已完成的 jobs"。
- **多一个常驻进程（约 100MB）**，在 2C2G 上是预算内但真实的成本。
- **本决策不覆盖"哪些任务该进队列"** —— 判据在实施时定：需要"提交后自动执行"或"定时/自动恢复"的进队列，一次性大任务优先走命令行。
- **一个已知要用队列的例子**：知识层增量期要定期扫「挂不上的题」并汇进**待定池**（决策 46）—— 那是周期性的，属于「定时」那一类，因此**走 worker 队列，不走命令行**；而首次装配（聚类 / 挂载）是一次性大任务，走命令行。
