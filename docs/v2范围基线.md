## 一句话边界

面向大众的 **AI 模拟面试平台**，核心是「AI 面试官」这一角色 —— 而不是面向单一岗位的个人刷题工具。
账号名额的硬性上限只为一件事存在：**控制 LLM 开销**。它是成本阀门，不是产品定位（不许把它当作"内测""小圈子"来论证任何设计取舍）。
_Avoid_: 刷题工具、personal tool、demo、内测产品

## In（v2 要做）

### 产品形态
三种，共享同一个**面试官**（区别于 v1：v1 只有「单题 + 追问」一种）：

| 形态 | 编排 | 额度点 | 输出 |
|---|---|---|---|
| **模拟面试** | 抽多题 → 逐题提问 → 每题追问 2-3 轮 → 收尾 | 6 | 面试总报告 |
| **单题追问** | 单题挖到深处 | 1 | 单题评分 + 反馈 |
| **题库刷题** | 自选题目，无 LLM | 0 | 自测；可看题干与评分标准 |

**模拟面试只有文字输出一种模态。** 语音输出（面试官 TTS 说话 + AI 数字人）已于决策 31**移出** —— 它的成本是文字输出的 10-30 倍，见下文「已评估但暂缓」。

**但语音输入要做**（决策 32）：面试页可语音回答，默认语音、可随时切回打字。这是**模拟面试真实感的关键** —— 打字框允许反复修改措辞，而真实面试考的是临场组织语言；v1 的 `clarity` 维度在打字模式下测的是排版，不是表达。

**语音输入不设「确认」这一步**（决策 33）：转写直接进判分，用户拿起麦克风就说话，没有"核对一遍再交"的环节 —— **术语识别错误交给 STT 模型与下游 LLM 的质量本身解决**，不靠人工核对兜底。判断候选人答得对不对、术语用没用对，本来就要读懂整段话；而"让用户先确认一遍"是把语音省下的打字成本又还回去。

首页 = **内容推荐中心**：开始模拟面试（主按钮）+ 今日推荐题 + 我的私有题集 + 继续未完成会话。**不做学习路径状态机。**

**同一时刻只允许一场未结束的面试**（决策 97）：还有没结束的（模拟面试与单题追问都算）就开不了第二场，首页把"开始"换成"继续 / 放弃"。所以必须有**放弃**这条路 —— 只堵不疏会把用户锁在一场他不想答完的面试里，而每轮追问都是一次真的模型调用。

> ⚠️ **「今日推荐题」是即时计算，不是每日锁定的题单**：`user_picks` 与 `questions.selected_at` 都随之删掉（见 `docs/v2数据模型.md`）—— 「今日题」作为**每日配额制的产物**消失了，而首页那个位置改由**按掌握度薄弱点现算**的推荐填充。它没有自己的表，也不跨天固化；换成别的推荐算法时它不会留数据残骸。

### 导航与信息架构
- 侧边栏（`base.html`）对**普通用户**是一级入口的**全集**：题库 / 收藏 / 私有题集 / 我的；owner 多一个「后台」。**「继续面试」只在真有答到一半的会话时才出现**（决策 96）
- **面试记录页** `/me/interviews`：整页的面试历史；`/me` 的「最近的面试」保留为摘要 + 一个"全部记录"入口
- 状态栏显示**今日额度点**（剩余 / 日上限，降级时补一句"纯题库"）—— 它解释"主按钮按下去会发生什么"（决策 13）
- 未登录时只有「题库」与「登录/注册」（登录页已有通往注册的链接，所以不单设注册项）
- **不做**：给首页单独加导航项（logo 就是首页）、签到/排行榜/成就这类增长装置、把反馈搬进侧边栏（低频）

### 内容
- **收藏夹**：候选人可以在**题库**里收藏题目，是首页的一个入口。收藏是**用户自己的指针**（`user_favorites`），题本身不动；动作幂等（`UNIQUE(user_id, question_id)`），**不消耗额度点**
- 内容来源三类：**种子题**（从 v1 迁移的题目 + 其题目级 `good_criteria`/`bad_criteria`）、**生成题**（LLM）、**晋升题**（用户私有题转入）
- 门禁：**自动门禁进池 + 事后治理**（人工不再前置逐题审）
- 知识层：**三层**，层级与表结构见 `docs/v2数据模型.md`；**岗位是独立的另一条轴、不在层级里**（决策 51/52）；骨架由 LLM 提议、**人审核**；挂题由 LLM 自动完成、靠答题数据自纠
- 每道题必须有一个**主知识点**（另可有 0..N 个**关联知识点** —— 决策 24）
- 知识层内容只有三类：骨架、知识点定义（1-2 行考察点）、泛用题的**参考答案**；**讲解/讲义按需生成 + 缓存，不预生成、不进审核队列**
- **不保留任何文档库**（v1 那批爬来的知识块整批丢弃，数量见 `docs/v1现状-20260913.md`）

### 简历与隐私
- 上传简历 → **解析成结构化候选人档案**（不保存简历原文）→ 生成**私有题集** → 面试从私有题集抽题
- 私有题集**用户隔离**；用户可主动**晋升**单题到公共题库（经内容门禁）

### 身份与成本
- 面向公众开放；**账号名额上限**是**成本阀门**（初期 10-20 人）
- **注册 = 邀请码**（后台生成、可设有效期、可作废回收）+ 邮箱作为登录名 + 密码；**不做邮箱验证码、不需要 SMTP**
- 忘密码 = 管理员后台重置；必须提供**注销账号与数据**入口（公开产品的法律底线）
- 额度 = **单一额度点**；耗尽后**降级**为纯题库模式（题库仍可用），不做硬拒绝
- 放弃一场未结束的面试时**按已答轮数返还**额度点（决策 98）：≤2 轮全额、3–6 轮一半、再往后不退；退到**当初扣点那一天**的账上，整数向下取整
- 后台同时记录真实 token 开销作第二道安全网
- 模型：**统一 `deepseek-flash`**（v1 的 `deepseek-chat`/`deepseek-reasoner` 已废弃；权威值是 `app/config.py` 的默认值）

### 部署与基础设施
> **本节只写范围** —— 决策、理由与它反推出的硬要求清单的权威处在 **ADR-0008**，本节不复述。

- 目标机器：**境外（美东弗吉尼亚）2C2G（上限 4C8G）单机**；因无法备案而选境外
- 网络与 TLS：Cloudflare 做 CDN 与访客 TLS，源站保持可移植
- 传输层：**TLS 是上线前置条件，不是待办**
- 存储：**SQLite + WAL**（调低页缓存）
- 备份：定时异地备份到对象存储，且**必须验证「能恢复」**
- 部署产物：**systemd 单元 + 定时器 + 反代配置 + 部署步骤**落在仓库根的 `deploy/`（决策 73/77）—— 其中"异地那一跳"仍在部署侧

### 架构
> **本节只列索引** —— 每条结论的权威定义在对应 ADR 里，本节不复述。

- 面试官是 **workflow（带循环的状态机）而非自主 Agent**；追问驱动 = 探测候选人的能力边界 → **ADR-0001**
- 知识层 = 关系库里的**森林 / DAG**，不用图数据库 → **ADR-0002**
- 面试报告由数据拼装，只有一段总结由 LLM 生成 → **ADR-0003**
- 前端**服务端渲染为主**，浏览器只负责面试页 → **ADR-0004**
- 代码**按领域切分、依赖单向**，跨领域动作归上层 → **ADR-0005**
- 离线任务用 **jobs 表 + 独立 worker**，不用 Redis → **ADR-0006**
- **prompt 独立成文件** → **ADR-0007**
- 部署在**境外单机**，Cloudflare + 源站可移植 → **ADR-0008**
- 嵌入**走 API**；删除本地模型 / 向量库 / 单进程锁；运行时只在「简历文本 → 知识点」一处用向量召回
- 交互：**SSE 流式**输出面试官说的话；**思考过程不展示**（但服务端记录用于调试）
- 从零重写：代码与架构全新；v1 的行为契约见 `docs/v1行为规格.md`

## Out（v2 明确不做）

| 不做 | 原因 |
|---|---|
| 爬虫（GitHub 采集、牛客采集、许可白名单、来源溯源、手写导入 CLI） | 面向公众后第三方内容的再分发风险无法靠代码消除；牛客源 v1 自己已放弃适配 |
| 人工前置逐题审核 | 吞吐瓶颈；改为自动门禁 + 事后治理 |
| 学习路径状态机 / 强制流程 | 用户随时可能只想刷两道题 |
| 本地向量库 / 本地嵌入模型 | 3000 条数据的全量点积是毫秒级；FAISS 解决的不是这个问题 |
| 独立知识库（文档切块 + 检索） | 被知识点定义取代 |
| 图数据库（Neo4j） | 几百个节点在内存里就是个字典 |
| 多向量库 / 多 embedding provider 的抽象层 | 没有第二个使用场景 |
| 内容管理 UI（分类/标签增删改） | v1 的 `admin/categories`/`admin/tags` 6 个端点随之消失 |
| 展示 LLM 思考过程 | 已明确 |
| **签到 / 排行榜 / 成就 / 关注等增长装置** | 对"练到能过面试"没有帮助。账号名额上限是**成本阀门**（见「一句话边界」），需要的是"更少的人用得更准"，不是拉更多人来刷 |
| **语音输出 / AI 数字人（TTS + 头像）**（决策 31 移出） | **技术上可行、已查实单价，但成本是文字输出的 10-30 倍**（一场约 0.6-1.7 元 vs 0.06 元）。注意：**语音输出的成本几乎全在 TTS，STT 便宜到可忽略** —— 所以只做语音输入（决策 32）不受此限。详见下文「已评估但暂缓」 |

| 98 | **放弃时按已答轮数返还额度点**：≤2 轮全额、3–6 轮一半、>6 轮不退；`refund_for_rounds(charged, rounds)` 整数**向下取整**，`rounds` = `attempts` 行数；返还走 `account.refund_units()`（一条语句 + `WHERE units_used >= :units`），记在**当初扣点那一天**的账上（`account.day_of(interview.started_at)`） | 决策 97 那条"放弃"的路把额度点的代价摆到了用户面前：一轮没答就丢掉 6 点（相当于当天 1/5 的额度）会让人不敢点。档位由用户定，实现上有三处必须写清：① **退到扣点那一天**，不是"今天" —— 额度按天重置，跨零点放弃时退到今天等于让今天凭空多出点数（`day_of()` 因此要把库里的 UTC 时间戳按配置偏移换算，测试里连"UTC 20:00 已经是次日额度日"这个坑一起钉住）；② **向下取整**：单题追问只有 1 点，"一半"是 0.5 → 退 0，而它最多答 3 轮（一题 × `max_rounds`），那一档只会落在"答满 3 轮"上；③ **幂等不能退第二次钱**（决策 97 的幂等只管"不报错"，这里补上"不重复退"）。`units_used` 不许退成负数（那会让 `remaining` 超过日上限、页面出现 `35/32`），所以条件更新里带 `WHERE units_used >= :units`，不成立就一行不写、返回 0。**页面上的数字与实际退款走同一个函数**（`refund_if_abandoned`）—— 两边各算一次迟早分叉成"页面说退 3、实际退 0"。⚠️ **记录在案的代价空洞**：≤2 轮全额返还意味着"开场 → 答 2 轮 → 放弃 → 再开场"可以**无限次免费用模型**（每轮都是一次真调用）。这条按用户要求照做，未加护栏；要堵的话最省的形状是"同一天里全额返还最多一次"（用 `interviews` 里今天 `abandoned` 且轮数 ≤2 的行数就能判，不需要新表）|
| 99 | **面试页两个出口语义分离**：「退出」= 只离开这一页（纯链接 `GET /`，**不写库、不改状态**，这一场还活着，「继续未完成」能回来接着答）；「放弃本场」= `POST /interview/{id}/abandon`（决策 97：结束这一场、置 `abandoned` + `ended_at`、释放"一场没结束不许开第二场"的闸、按决策 98 退点）。同时**撤掉** `interview.js` 里那道"压历史记录拦浏览器后退"的挡板 | 此前答题页上唯一的出口叫「放弃本场」，而**离开这一页**在界面上没有别的路（导航被考场模式接管了）—— 于是"我只是想走开"被写成了"我要结束这一场"：状态被置 `abandoned`、闸被松开。用户的判断是**两个动作本来就不是一回事**，所以拆开，并且这次**明确不做**下面两件（都讨论过，都记在这里免得被重新发明）：① **不新增终态**（`interviews.status` 仍是三值，加第四个值要改 `0001` 的 `CHECK` 即重建表）；② **不留"部分结果"**（退出与放弃都不产生分析页，`/me/interviews` 的"看报告"仍然只认 `finished` 那一份）。⚠️ **一条容易被当成 bug 的现状**：放弃掉的那几轮**照样计入掌握度矩阵** —— `knowledge.service._hit_blobs_for_user()` 只按 `user_id` 过滤，**不看 `interviews.status`**（每轮的 `hits` 在作答时就落库了，`app/interview/service.py` 的每次 `run_round` 都写一行 `attempts`）。差别只在"有没有一份可回看的分析页"，不在"算不算"。这条以前是隐式的，现在写下来了；要改成"放弃就从矩阵里去掉"，得给矩阵加一条排除规则（`/me` 与报告两处都走它）——那是另一个决定，不是这个。③ **答题页（含"这场已经放弃"那一支）带 `Cache-Control: no-store`**：两个出口都靠"离开这一页"生效，而浏览器会把整页放进 back/forward 缓存、按返回键复原它 —— **实测**：放弃之后点返回，那个看起来还能答的界面又回来了（提交只会撞 409）。`no-store` 让返回键变成一次真请求，服务端渲染的才是真实状态 |
| 100 | **模拟面试的抽题从"最近三道"改成"薄弱点优先 + 排除答过的"**（用户自选的两条：A 排除已答、C 按掌握度）：装配层按这个顺序凑满 3 道 —— ① `knowledge.mastery_matrix().weak_points(limit=5)` 给出的薄弱知识点下、且**该用户没答过**的题；② 不足 3 道时，用**全库没答过**的题补满（`bank_service.latest` + `exclude_ids`）；③ 还不足（题库小 / 全答过）才放开"没答过"这条，退回最新 3 道。**不引入随机**：同一份库状态永远选同一套，顺序仍然确定 | **实测的坏形态**：现场库里连着四场模拟面试抽到的是**同一套三道题**（3021/3022/3023，各出现 4 次）。根因是旧规则只有一句"`visible_to` + `id` 倒序 + `limit=3`"—— 它抽的是题库里 id 最大的三道，而 id 最大的恰好是离线生成的几道；**只要不往库里插入新的可见题，开一百场都是这套**，与"上一场有没有答完"无关（题数在开场时就定死了）。这条同时补上 A 与 C：排除"答过"用的是现成的 `interview.answered_question_ids()`（首页推荐一直在用它），选"薄弱点"用的是 `mastery_matrix().weak_points()` —— **两处与首页同源**，不新造第二套判据（否则"首页推的题"和"面试抽的题"迟早各说各话）。⚠️ 三条边界写清楚：① **薄弱点只算"考过且没答到"的格子**（`weak_points()` 的定义），没考过的知识点不算薄弱，所以新用户走的是第②条；② 场上仍然是 **3 道**（`INTERVIEW_QUESTION_COUNT`，本次不动）—— 凑不满时"少给几道"比"给重复的题"好；③ 每次开场自己查一次掌握度（一条聚合查询），**不落"本场计划"以外的新状态**（`interviews.plan` 里仍然只有 `question_ids`）。**没做的**：按知识点分层抽样（让覆盖更均匀）与"题目难度递进"——那要另定判据，不在这次里 |
| 101 | **模拟面试的形态改成 8 题 × 每题最多 3 轮**（用户定：8 道题、每题最多追问两轮 ⇒ 用户每题最多回答三轮）：`INTERVIEW_QUESTION_COUNT` 3 → 8，`DEFAULT_MAX_ROUNDS` 保持 3（它是**总轮数**，`rules.should_finish` 判 `round_no >= max_rounds`，所以"最多追问两轮"正好是 3，不是 4）。一场最多 24 轮 | 这是用户明确的形态要求，改的是两个常量，但它**同时是成本参数**：单场模型调用次数从 ≈12 涨到 ≈32（≈ 84k token，按决策 71 的实测单价），而 `COST["interview"] = 6`、每日上限**都不跟着改** —— 用户的原话是"就给 32 点数，一场 6 点，用着呗"。所以这里**记下这笔账**而不是偷偷改系数：① 6 点/场 对应的是"12 次调用"那一档，现在实际是 32 次 ⇒ 每场约白送 15 轮；② 标定过的每日上限是 **8 点**（`CALIBRATED_DAILY_UNITS`，决策 71），8 点在新形态下只够开 **1 场**（旧形态够 1 场 + 2 轮追问）；③ 本机跑的是临时测试值 `DAILY_UNITS = 32`（源码注释里已声明"测试完请改回来"），按现在的账是"一天 5 场"。**要按成本重标定的话是一个独立决定**（会连带改决策 71/98 的推导与 `migrations/0001_initial.sql` 里 `quota_charged` 的注释，而迁移是校验和冻结的），不在这次里做。另：现有"连续两轮没有新命中就收尾"（`dry_rounds=2`）把实测轮数压到 2-3 轮/题，所以真实调用次数通常低于 32；单场时长从约 10 分钟涨到约 25-35 分钟 |

## 换模型的影响范围（决策 50 的连带纪律）

按用途分开命名之后，「换模型」这件事的影响范围才是明确的：

| 换哪个 | 必须做什么 |
|---|---|
| `MODEL_INTERVIEWER` | **面试官相关的 prompt 全部重测**（追问、判分）—— 换模型必须重测 prompt，这是 `v1行为规格.md` §4.10 已定的纪律 |
| `MODEL_OFFLINE` | 聚类 / 挂载 / 生成 / 质检的 prompt 重测 |
| `MODEL_EMBED` | 不需要重测 prompt，但**全部已存向量作废、必须重算** |

⚠️ **最后一条最容易被忘记，而且它不报错**：嵌入模型一换，库里旧向量与新算向量**不在同一向量空间**，相似度比较会静默给出垃圾结果。所以换嵌入模型时必须有一个「重算全部向量」的步骤，而不是只改配置值。

## 已评估但暂缓：语音输出（面试官 TTS / AI 数字人）

> **决策与形态判断的权威在 ADR-0009** —— 本节只留成本证据与实施坑清单，不复述决策。

**注意：暂缓的是「语音输出」，不是「语音」。语音输入要做**（决策 32）。两者成本差 13 倍，见下表。

### 关键区分：贵的是 TTS，不是 STT

```
语音输入（用户说 → 转写）    STT  8 分钟 ≈ 0.13 元/场  ← 便宜到可忽略
语音输出（面试官说 → 朗读）  TTS  3000 字 ≈ 0.24-1.50 元/场  ← 成本几乎全在这里
```

**所以「暂缓语音输出」不影响「做语音输入」。**

### 形态判断（若将来做）

「数字人」三个字背后是差别极大的三种东西：**音频 + 会动的头像**（CSS 动画，近零成本）／**音频 + 口型同步**（Live2D 级）／**真数字人视频**（按分钟计费，单场可能几美元）。**选前者** —— 面试的紧张感来自"要说出口"，不来自"看得到嘴型"。

### 真实单价与成本（决策 31 查实）

| 项 | 服务商与单价 | 一场 15 分钟的成本 |
|---|---|---|
| **STT** | 豆包流式语音识别 2.0：**1 元/小时** | 用户说 8 分钟 ≈ **0.13 元** |
| **TTS（贵档）** | 豆包大模型语音合成：**5 元/万字符** | 面试官说 3000 字 ≈ **1.50 元** |
| **TTS（中档）** | 豆包语音合成 2.0：**3 元/万字符** | ≈ 0.90 元 |
| **TTS（便宜档）** | 阿里 qwen3-tts-flash：**0.1147 USD/万字符** ≈ 0.83 元/万字符 | ≈ **0.24 元** |
| LLM | deepseek-flash（已有） | ≈ 0.06 元 |

**关键发现：TTS 是唯一的成本大头，且不同档次差 5-6 倍；STT 便宜到可以忽略。**

| 组合 | 一场成本 | 20 人 × 每日 1 场 = 每月 |
|---|---|---|
| 豆包 + 大模型 TTS | ~1.7 元 | **约 1000 元** |
| 阿里 qwen3-tts | ~0.6 元 | 约 360 元 |
| **纯文字（对照）** | **~0.06 元** | 约 36 元 |

**语音把成本乘以 10-30 倍** —— 而「10-20 个名额」这个成本阀门是按文字算的。

### 实施时需要注意的坑（若将来重启）

- **并发要买**：豆包默认并发 5-50 路，超出 **100 元/并发/月**
- **音色可能收费**：音色槽位 138 元/音色起 —— 但**赠送音色免费**，只需要"一个面试官的声音"，**不要复刻音色**
- **确认流式**：阿里 qwen3-tts-flash 标注为「**离线**语音合成」，若只有非流式接口，首句要等整段合成完，延迟会明显劣化 → 需确认是否支持流式
- **网络路径是隐藏硬约束**：服务器在美东、用户在境内，语音是双向实时流。绕美国会明显劣化 → 大概率需要**客户端直连语音服务**（绕过应用服务器），而这要求服务商支持前端鉴权（临时凭证 / 签名）
- **必须处理「用户打断面试官」**：语音交互里最容易被忽略、但不处理就假得刺眼的地方

### 它动摇过哪些已定决策（记录，供将来重启时参考）

| 已定决策 | 若做语音的影响 |
|---|---|
| 统一 `deepseek-flash` | ❌ **不够** —— DeepSeek 无 STT/TTS，必须引入语音服务商（第 2、3 个外部依赖） |

## 掌握度的定义（决策 24 的结论，重要）

```
掌握度矩阵的每一格 = 该知识点下「被考过的考察点」里，候选人答到了多少
                    （不是分数，也不是题量）

它只依赖 hits（逐轮产出），与「这道题挂在知识地图的哪个节点下」无关。
```

三条推论：

1. **「没考过」是空格，「考了但没答」是 0%** —— 两者对候选人的含义完全不同，必须可区分。这要求命中记录在用户完全没答时也要记未命中，而不是只在答到时才有数据。
2. **一道综合题会同时填充多个格子** —— 库里真题 1065（设计一个可靠的 Agent 系统，要求支持幂等/熔断/限流/成本/权限/可观测）一道题就能在六个知识点上留下记录。
3. **不需要给「题目 ↔ 知识点」的关联加权** —— 权重问题被「格子装命中率而非分数」消解掉了。

## 测试策略（决策 75）

**不搬 v1 的用例。** v1 那 471 条里只有约 1/3 有搬运价值，而 v2 的行为已经变了
（ADR-0001 换了编排、额度点取代了每日上限）—— **搬运一份已经改义的断言比没有断言更糟**：
它绿着，但保的是旧行为。分类见 `docs/v1行为规格.md` §12。

**纪律写成可执行的断言。** 一条只住在文档里的规则迟早会被绕过（"写进文档容易、忘掉
更容易"），所以能用结构断言表达的纪律就不留给记忆：

| 纪律 | 可执行形式 |
|---|---|
| 题目查询只走 `bank/repository` 的统一入口（§3.5） | `app/bank/test_repository.py` 用 AST 扫全 `app/`，只看真实的 `Call` 节点（纯文本与正则都误报过） |
| `JsonText` 必须 `ensure_ascii=False`（规则 21） | `scripts/check_docs.py` 用 AST 认 `json.dumps(...)` 的关键字，多行写法也不会漏 |
| 迁移不许挂在启动上（ADR-0008 / 决策 55） | `tests/test_deploy_units.py` 逐行解析单元文件 |
| 部署单元里的命令必须真的存在 | 同上 —— 判据是跑一次 argparse，不是比字符串 |
| 不许直接 `select(Question)` / 不设无界进程内状态 | 前者见上；后者的判据是"每个缓存都配一条 TTL 回收的测试"（`app/ratelimit.py`、`explanation.py`） |

**不设覆盖率门槛。** 覆盖率能靠加无断言的测试刷高（`assert True` 也是"覆盖"），
而这里要求的是另一件事：**每条新测试都要做过一次变异验证** —— 把被测代码改坏、
看它红不红；红不出来的测试等于没写。这条纪律没有门槛能替代，也不需要门槛：
一个要靠百分比才能维持的标准，本来就已经在退化。

**明确不测的**：prompt 文字的"好坏"（那是模型与提示词评审的事，不是断言）、
真实供应商的连通性（用替身，真调用只做一次性冒烟）、界面样式（ADR-0004）。

## 验收标准（已定于决策 74）

**一条标准只有配上"怎么验"才算数** —— 否则它会在项目末期变成一场关于措辞的讨论
（"三种形态都能完整跑通"里的"完整"谁都解释得通）。下表每条都写清判据落在哪里：
能自动验的写测试或命令，验不了的**老实写"人工/演练"**。

| 判据 | 怎么验 |
|---|---|
| 三种形态都能完整跑通，共享同一面试官 | `app/interview/test_service.py`、`app/web/test_interview_pages.py`、`app/web/test_voice_page.py` |
| 额度点扣减准确；耗尽后题库可用 | `app/web/test_quota_degradation.py`（含"还剩 3 点不是纯题库模式"那一条） |
| 全部题已按知识点归位，挂载错误能被答题数据发现 | `python -m app.cli status`（待定池那一行应为 0）；`app/bank/test_quality.py`（`suspect_mount` 检测） |
| 一道综合题同时更新多个知识点的掌握度 | `python tools/verify_composite_question.py` —— 挑一道挂在 ≥2 个点上的题（实测 #920 挂了 3 个）、真作答、打印掌握度矩阵，判据是"牵动 ≥2 个格子"；`app/knowledge/test_mastery.py` 管机制 |
| 「没考过」与「考了但没答」在矩阵上可区分 | `app/knowledge/test_mastery.py`（三值命中状态） |
| 流式输出中断时数据不丢（开始写/结束写/中断写三段式） | `app/web/test_interview_pages.py`、`app/web/test_voice_page.py` |
| 无进程内无界状态；无 async 上下文中的同步 DB 查询 | `app/test_ratelimit.py`（TTL 与容量回收）；**人工**：改路由时自查 `app/deps.py` 的同步依赖约定 |
| 所有降级都有用户可见状态 + 可查询记录（不静默） | `test_interview_pages.py::test_llm_failure_is_visible_to_the_user_not_silent`、`app/offline/test_calibration.py`（失败也打出来） |
| TLS 是部署文档里的前置条件，不是待办 | `tests/test_deploy_units.py`（README 里那三个开关）；`deploy/README.md` |
| 带着占位口令的库**拒绝启动**（决策 58） | `app/db/test_constraints.py::test_startup_check_refuses_a_placeholder_password` |
| §11 的每个数字都有对应的实验脚本与结论 | `python -m app.cli calibrate`（决策 70）+ 台账 70/71/72 的结论 |
| 备份**验证过能恢复**，且演练过 | `python -m app.cli verify-backup <文件>`；**演练**：每季度真恢复一次（`deploy/README.md`） |

这张表**有执行器**：`python scripts/check_acceptance.py` 逐条真的跑（跑对应测试、
查库、做一份备份并当场验证），打印 `PASS / FAIL / BLOCKED / MANUAL`，没过的以非零
退出码结束。`BLOCKED` 表示「前置条件还没满足」（例如装配还没跑，所以「待定池为 0」
必然不成立）—— 它**不算失败**：把「还没到那一步」算成失败，结果是所有人学会忽略它。
它自己的有效性由 `scripts/selftest_check_acceptance.py` 用变异证明（一个永远返回
PASS 的执行器比没有执行器更糟）。

最后两条（无 async 同步查询、备份恢复演练）**刻意留作人工** —— 这不是遗漏，而是
"能自动化的那部分已经自动化了，剩下的写清是人来做"。把它们写成自动检查会让检查
**变形**：为"无 async 同步查询"写一条正则，然后所有人学会绕过它。

> **综合题那条已经不是人工了**（实测改过一次口径）：它原先写"人工用真题 1065 走一遍"，
> 而 1065 与演示库那六个知识点的名字**真的不相关**（模型把它退回待定池是正确行为，
> 决策 46）—— 那条判据当时其实**验不了**。现在库里真有 78 道挂在 ≥2 个点上的题，
> 于是它变成了可复跑的脚本：`tools/verify_composite_question.py`。
