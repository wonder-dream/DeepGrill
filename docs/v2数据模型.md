# v2 数据模型（从已定决策反推）

> 状态：会过期（实现后由代码里的模型定义与迁移脚本替代）｜ 被什么替代：代码里的模型定义 + 迁移脚本；届时只保留「为什么这么设计」的部分（已在 ADR 里）。

> 本文不是提案，是**推导结果**。每张表都标注它由哪条 ADR 或决策产生。
> 依据：`CONTEXT.md`（术语）· `docs/adr/`（**全部**架构决策，不止与表结构直接相关的那几份）· `docs/v2范围基线.md`（决策台账）。

## 结构总览

```
账号侧        users ── invite_codes ── user_tokens
              users ── quota_ledger（每日额度点 + 月度归档行）

知识侧        domains（森林：多个根，parent_id IS NULL）
                 └── 知识领域 ── 子领域 …
              knowledge_points（domain_id → domains）── criteria（知识点级考察点）
                    │
                    ├── knowledge_point_edges（前置依赖，可有跨领域边）
                    └── roles ── role_points（岗位是另一条正交的轴）

题库侧        questions ── primary_point_id ──→ knowledge_points   ← 每题必属一个知识点
                  │
                  ├── question_points（还牵动哪些知识点，多对多）
                  └── question_flags（矛盾记录 / 挂载可疑）

私有侧        users ── candidate_profiles ── questions（私有题集，带 owner）

作答侧        users ── interviews ── sessions ── attempts
                           │            └── evaluations
                           └── report_items（含判分依据快照）

治理侧        question_feedback / question_point_stats / jobs / task_logs / schema_migrations
```

## 1. 账号侧

### `users`
由**决策 6**（邀请码注册）产生。v1 的 `focus` / `focus_lang` **删除**。

> ⚠️ 注意区分（决策 51）：**目标岗位仍是用户的属性**，只是不再存成 `focus` 字段；被移出的是「岗位作为**知识地图**的一层」。岗位与知识点的关系改由 `roles` / `role_points` 表达。

| 字段 | 说明 |
|---|---|
| id | |
| email | UNIQUE，登录名 |
| username | 显示名 |
| password_hash | `scrypt$salt$digest`（继承 v1） |
| role | owner / user |
| created_at | |

> **没有 `deleted_at`**：注销走**硬删**（决策 21）—— 删掉身份与原文，只把判定数据聚合进 `question_point_stats`。软删除字段因此不需要。
>
> ⚠️ **硬删必须按顺序，否则会被外键拦住**：v1 有 `FK CASCADE`、v2 **一条都没有**（`0001_initial.sql` 里全是普通 `REFERENCES`，虽然迁移 runner 会打开 `PRAGMA foreign_keys`）。而 `invite_codes.created_by` / `used_by` 是**自引用到 `users`** 的，删用户会直接撞约束。顺序（决策 61）：
>
> ```
> ① 先把该用户的 attempts.hits 累加进 question_point_stats（线 1 → 线 2，见 §9 风险③）
> ② UPDATE invite_codes SET created_by=NULL WHERE created_by=?；
>    UPDATE invite_codes SET used_by=NULL    WHERE used_by=?     ← 码本身要留，它是发放记录
> ③ DELETE user_tokens / quota_ledger / candidate_profiles
> ④ DELETE question_feedback？→ 不删，只 UPDATE ... SET user_id=NULL
>    （user_id 本来就可空 = 匿名反馈；这也让"反馈还在、人已注销"成立）
> ⑤ DELETE interviews（其子表 sessions / attempts / evaluations / report_items 由其先删，或由业务层按层删）
> ⑥ DELETE questions WHERE owner_user_id=?（私有题集）
> ⑦ DELETE users
> ```

### `invite_codes`
**新表**。由**决策 6**（邀请码注册）产生。取代 v1 的 `MAX_USERS` 全局计数 + `email_code` 整套。

| 字段 | 说明 |
|---|---|
| code | UNIQUE |
| created_by | → users |
| expires_at | 可空（永久有效） |
| used_by / used_at | 空 = 未使用；可作废（删除行） |

> `MAX_USERS` 这个名字随之消失 —— 名额由「发了多少码」决定，而不是一个全局计数器。

### `user_tokens`
沿用 v1 设计（库里只存 sha256、有 TTL、可撤销、惰性清理过期行）。

| 字段 | 说明 |
|---|---|
| token_hash | **主键**。明文的 sha256 —— 明文只出现在 cookie 里，库里没有 |
| user_id | → users |
| expires_at | 过期时间。惰性清理：读时判过期，不靠定时任务 |
| created_at | |

> 这四列原先只写了"沿用 v1 设计"一句，等于**不可审**（读者无法从本文核对 v2 建得对不对）。补全的依据是 `docs/v1现状-20260913.md` 与 v1 的实际表结构；安全约定本身在 `docs/v1行为规格.md` §9。

### `quota_ledger`
**新表**。由**决策 13**（单一额度点）与**决策 14**（另记 token 开销）产生。

| 字段 | 说明 |
|---|---|
| user_id / kind / day | 复合唯一。`kind` = `day` / `month` |
| units_used | 已消耗额度点 |
| tokens_used | 真实 token 开销（第二道安全网） |
| updated_at | |

> 记**每日一行**而非每次一条流水：用户只需要知道"今天还剩多少"，而你需要知道"钱花在哪了"。
> 另加**每月一条归档行**（决策 23）：这样既能回答"上季度花了多少"，又不必保留全量流水。
>
> ⚠️ **两种粒度必须显式区分**：`kind='day'` 的行 `day` 是 `YYYY-MM-DD`，`kind='month'` 的行是 `YYYY-MM`。第一版打算"用一个特殊 day 值如 `2026-09`"来区分 —— 那让同一列混两种格式，而"这个月已用多少"只能靠字符串形状猜。加一列 `kind` 把它变成显式事实（表是空的，不需要迁移数据）。

## 2. 知识侧（ADR-0002 的图）

知识层是**三层**，只有前两层需要人审：**知识领域**（十几个顶层，组织成森林）→ **知识点**（几百个，人审关键）→ **考察点**（上千条，LLM 生成 + 抽查）。**考察点独立成表** —— 这是"复制传播"判据能落地、考察点能复用的前提。

### `domains`
知识领域的层级结构，由 `parent_id` 自引用表达。**它是森林，不是一棵树**（决策 52）：顶层领域有多个，`parent_id IS NULL`，**不存在虚构的"全部知识"根节点**。

| 字段 | 说明 |
|---|---|
| id / parent_id / name | 顶层领域 `parent_id IS NULL` |

> **为什么是森林**：Java 并发、RAG 检索、推理优化之间没有任何父子关系，它们本来就是并列的（实测约十几个领域）。造一个虚构的根只是为了让遍历代码好写，却会**掩盖"这些领域彼此无关"这个真实结构**。
>
> ⚠️ **它也不是树，而是 DAG** —— 因为知识点可被多条路径共享（跨岗位复用）。「树」这个词在本文里一律按"有向无环图"理解。
>
> ⚠️ **没有 `kind` 字段**：岗位**不在**这张表里。岗位是另一条正交的轴（见下 `roles` / `role_points`）。
>
> ⚠️ **两种关系分开存**：层级走 `parent_id`（"它属于哪个领域"），依赖走 `knowledge_point_edges`（"它依赖什么"），后者允许跨领域。
>
> 💡 **实现提示**：领域表只有几十行 —— **一次 `SELECT * FROM domains` 拿全、在内存里拼层级**，不要写递归 CTE。既简单又避开了 SQLite 递归查询的版本差异。

### `roles` / `role_points`
**新表**。岗位是**独立于知识结构的另一条轴**（决策 51）。

| `roles` | 说明 |
|---|---|
| id / name | 岗位词表（ai_app / ai_infra / backend / frontend / qa …） |

| `role_points` | 说明 |
|---|---|
| role_id / point_id | 复合主键：某个岗位要考哪些知识点 |

> **为什么岗位不能当知识地图的根**：① 「市面上有哪些岗位」是**市场维度**，「知识怎么组织」是**知识维度**，两者在真实世界里正交（同一岗位要多个领域，同一领域服务多个岗位）；② 若岗位是根，用户换岗位就换一棵树，而**掌握度矩阵是跨场聚合的，它需要一个稳定的坐标系**；③ 用户在设置里选的是"我要面 ai 应用岗"，不是"我要考 JMM" —— 所以岗位这层映射必须存在，只是不该长在地图里。
>
> ⚠️ **它补上了现状里一个真空**：在此之前，数据模型里**没有任何"岗位 ↔ 知识点"的关联**，"按岗位抽题"无从实现。这正是 v1 把 `roles` 塞进标签表的原因 —— 它需要这个映射，就顺手塞进了标签里。
>
> ⚠️ **`role_points` 的内容需要初始化**（哪个知识点属于哪个岗位）—— 可以 LLM 提议、人审，与知识地图的构建同一套路。

### `knowledge_points`
知识地图的**第 2 层**节点。人审的对象，v2 的核心资产。

| 字段 | 说明 |
|---|---|
| id / name | |
| **domain_id** | **属于哪个知识领域**（`domains.id`）—— 「知识领域 → 知识点」这层关系在库里的唯一表达 |
| status | draft / confirmed（**人审过才是 confirmed**） |
| origin | proposed（LLM 提议）/ manual（人写） |
| exclusions | **不考察什么**（防止挂载漂移） |
| question_count | 挂在此节点下的题数（用于审核分层：≥20 / 10-19 / 5-9 / 3-4 / ≤2） |

> ⚠️ 一条知识点下的考察点通常 2-5 条。**如果写不出「什么算答到、什么算没答到」的考察点，这个知识点就切错了**（判据 1）。
>
> ⚠️ **`question_count` 是缓存，不是事实源**：事实源永远是 `questions.primary_point_id` 的计数。这一列存在只是为了审核分层（ADR-0002 的分档表要按题量排期）。**维护者与时机还没定** —— 唯一的硬要求是：它必须由 `bank` 领域在写题时维护（ADR-0005：写 `questions` 表的只有 `bank`），否则它会变成第二个会漂的真相。分层决策若与它不符，以 `COUNT` 实测为准。
>
> ⚠️ **`domain_id` 不能省**：没有它，「知识领域 → 知识点」只是文档里的一句话 —— 三层结构（决策 26）在库里无法表达，而 `docs/知识层构建管道.md` 第 6 步「限同领域、限深 ≤2」的「同领域」也没有判定依据。**一个知识点属于一个领域**（多对一）；要表达跨领域的关系走 `knowledge_point_edges`（依赖）或 `role_points`（岗位），不在地图层里加第二根轴。

### `criteria`
**新表**。**考察点单独成表**，而不是塞进 `knowledge_points` 的 JSON 字段。

| 字段 | 说明 |
|---|---|
| id / point_id / seq | 属于哪个知识点的第几条 |
| text | 一条可逐条判定的考察点（如"保证可见性与有序性，不保证原子性"） |
| shared | **共用考察点**标记 —— 通用表达类考察点允许被多个知识点合法引用 |

> **为什么必须独立成表**：判断两条考察点是否"不该复制"（判据 2 · 复制传播）需要一个**稳定的 id** 来跨知识点比较。若把它塞成 JSON 字段，这个判据就无法自动计算。同时它也是 `attempts.hits` 与 `question_point_stats` 的引用对象。
>
> ⚠️ **`shared` 是判据② 的前提，不是装饰**：它要区分两件长得一样的事 —— 一条考察点被复制到多个知识点下（**该合并**），与一条通用表达类考察点（"先说结论再说理由"）出现在多处（**不该合并**）。ADR-0002 已把「显式标记为共用考察点」写成决策，而第一版 schema 漏了这一列 —— 于是那条判据只能吃误报。

### `knowledge_point_edges`
前置依赖边在这里；「矛盾」见 `question_flags`。**岗位不走边** —— 它是另一条正交的轴（见上面 `roles` / `role_points`）。

| 字段 | 说明 |
|---|---|
| from_point_id / to_point_id / kind | `prerequisite`（前置依赖，有向、无环） |

> 前置依赖**定义在知识领域内**，但允许跨领域的边（"RAG 依赖向量检索"，而它们在两个领域）—— 因为依赖是**知识本身的性质**，与求职岗位无关。
> 「矛盾」不在这里，见 `question_flags`。

## 3. 题库侧

### `questions`

| 字段 | 说明 |
|---|---|
| id | |
| kind | **knowledge / design** 两类（决策 20）；**项目深挖题只存在于私有题集** |
| stem | 题干 |
| difficulty | 1-5（继承 v1 的定义与标定） |
| primary_point_id | **必填**（可空只是为了 v1 导入容错，见下），题挂在知识地图的哪个节点下（导航 + 挂载自修复用；**不参与掌握度计算**） |
| good_criteria / bad_criteria | **离线素材**，不是产品数据 —— v1 的题目级 criteria 原样导入（题量见 `docs/v1现状-20260913.md`），供知识层构建管道当聚类素材（见下方纪律） |
| answer_tier | 泛用档 / 长尾档 —— 即**参考答案**的有无。**泛用题预生成答案、冷门题只有评分标准**（**决策 12**） |
| reference_answer | 仅泛用档有；长尾档为空（按需生成） |
| origin | seed（v1 迁移）/ generated（LLM）/ promoted（从私有题集晋升） |
| owner_user_id | 非空 = **私有题集**的题；空 = 公共题库 |
| visibility | public / private / pending（晋升待门禁）/ hidden（质量信号差） |
| created_at | |

> ⚠️ **两套评分依据必须区分清楚（决策 49 纪律）**：
>
> | | `questions.good_criteria` / `bad_criteria` | `criteria` 表 |
> |---|---|---|
> | 粒度 | **题目级**（每道题一份） | **知识点级**（归并后的考察点） |
> | 角色 | **离线素材** —— 知识层构建管道的聚类输入 | **产品数据** —— 判分、掌握度、报告都读它 |
> | 会不会漂移 | 导入后基本不变 | 会随你审知识点定义而变 |
>
> **硬规则：任何运行时逻辑（判分 / 追问 / 掌握度）只准读 `criteria` 表。** `questions.good_criteria` 只有两个合法读者：离线管道（聚类素材）与 `report_items` 的**快照**（历史证据，不参与判分）。
> 违反这条不会有报错，只会让判分悄悄用上一份没人再维护的旧标准 —— 所以它写成规则而不是约定。
>
> **为什么题目级 criteria 要进 v2 库**（而不是留快照或读 v1 库）：它让 **v2 库自足** —— 删掉 v1 目录后，重建知识层仍然做得到；而且初始装配与增量维护因此走同一条路径（都对着 v2 库跑），不会分叉。

**删除的 v1 字段及原因：**

| v1 字段 | 为什么删 |
|---|---|
| `source_id` | 爬虫源整条删除；`origin` 取代它表达"题从哪来" |
| `reviewed_at` | 人工前置审核取消；`visibility` 表达同一件事且支持分步公开 |
| `selected_at` | 「今日题」概念消失（首页不再是每日配额制） |
| `embedding` | 嵌入走 API 且不在题目表里；运行时几乎不做向量检索 |
| `tags` 多对多 | 被 `primary_point_id` + `question_points` 取代（`question_tags` 表删除） |

### `question_points`
**新表**。题目**还牵动了哪些知识点**（决策 24）。

| 字段 | 说明 |
|---|---|
| question_id / point_id | 复合主键 |
| source | `authored`（出题时确定）/ `inferred`（LLM 事后推断） |

> 为什么需要它：一道综合设计题会牵动多个知识点（真题 1065「设计一个可靠的 Agent 系统」牵动幂等、熔断、限流、成本控制、权限模型、可观测性六项）。若只挂一个节点，用户在「限流」上被考过却永远显示未做 —— **掌握度矩阵会系统性低估**。
> 它用于：按知识点组卷、能力覆盖检查。**不用于掌握度归属** —— 那走 `hits`。

### `question_flags`
**新表**。矛盾记录 + 挂载可疑（ADR-0002 的"自修复"落地处）。

| 字段 | 说明 |
|---|---|
| question_id | |
| kind | `conflict`（与同知识点其他题口径不一致）/ `suspect_mount`（长期答不到本知识点的考察点）/ `suggest_move` |
| detail | 证据（比如：连续 N 场无人答到本节点的考察点） |
| status | open / resolved / dismissed |

> 这张表就是 ADR-0002 说的那个「题库哪里不干净」的仪表板。它让挂载错误**可观测**。

> 这一节的决策：**决策 8**（简历 → 候选人档案 → 私有题集）与 **决策 9**（用户隔离 + 晋升）。

简历解析产物。**不保存简历原文**。

| 字段 | 说明 |
|---|---|
| user_id | |
| structured | JSON：项目 / 职责 / 技术栈 / 量化结果 |
| source_note | 可选，用户自己写的备注（不存原文） |
| created_at | |

### 私有题集
**不是一张新表** —— 就是 `questions` 里 `owner_user_id` 非空的行。

> 好处：判分、展示、晋升**全部复用同一套代码路径**；晋升 = 把 `owner_user_id` 置空 + 走内容门禁 + 重新走挂载。坏处：`questions` 表承担两种可见性语义，需要索引与查询纪律保证不漏过滤（**这是 v2 最容易出的越权 bug 点**）。

## 5. 作答侧（**决策 19**：两层会话结构）

### `interviews`
第一层。**新表**，v1 完全没有对应物。

| 字段 | 说明 |
|---|---|
| id / user_id | |
| mode | interview（完整面试）/ drill（单题追问）—— **`browse` 题库练习不建 `interviews` 行**（见下） |
| plan | 编排配置 + **调整日志**：初始题单（题目 id 列表）/ 每题追问轮数上限 / 是否要报告；以及面试过程中编排层的每次**跳过**与**插入**记录（ADR-0001 决策 25 补记） |
| status | active / finished / abandoned |
| quota_charged | 创建时扣的点数（0 / 1 / 6） |
| report_body | **finish 时算好的报告主体**（JSON）：矩阵变化 ② / 主要问题清单 ⑤ / 前置缺口 ④。这几块依赖「本场之前」这个时间点，事后重算可能与当时不同 |
| report_summary | **那段 LLM 总结 ⑥**。存库（不现生成）—— 否则每次打开措辞都会变，与「报告不重新生成」矛盾 |
| started_at / ended_at | |

> **`plan` 为什么不能只是一张固定题单**：编排层在每道题结束后读本场已产生的判定结果，可以**跳过**一道与刚失败的下游知识点相关的后续题，或**插入**一道前置知识点的题（跳过 ≤ 计划题数的 1/3、插入 ≤ 2 道，总题数不变）。调整必须留痕，否则报告无法解释"为什么这场只问了 5 道而计划是 6 道"。
> 信号来源是逐题的判定结果 —— **不是一个新的能力模型**。

> ⚠️ **`browse` 不属于本表**：题库练习按 `CONTEXT.md` 的定义「不进入面试、也没有**编排**」，且额度点为 0、不调 LLM。给它建一行 `interviews` 等于让数据模型承认一种它已经不承认的形态 —— 而 `sessions.question_id NOT NULL` 又要求每条会话必须有一道题，于是"浏览"还得挑一道题来占位。**题库浏览的进度与收藏另行记录**（收藏见 Open-5），不借道面试会话表。
>
> ⚠️ **「每用户同时只有一个 active interview」是业务层规则，不是库约束**：`0001_initial.sql` 里只有 `sessions` 的 `(interview_id, seq)` 唯一，没有"每用户一个 active"的部分唯一索引（v1 的 `uq_sessions_active` 是索引）。这是一次**有意的降级**：模式串行化（答题页只有一个）由 service 层保证。后果是「继续未完成会话」这个首页入口必须**自己定义**怎么在多个 active 里挑一个（建议：取最近 `started_at` 的一个），而不是假设只有一个。

> ⚠️ **逐题回顾不在本表** —— 它拆成 `report_items`（见 §5 作答侧），因为需要**快照**判分依据，而 JSON 大字段改一行要回写整块。

### `report_items`
**新表**。面试报告的每一道题一行，**含判分依据的快照**（决策 24 风险④）。

| 字段 | 说明 |
|---|---|
| id / interview_id / session_id | |
| seq | 本场第几题 |
| snap_stem | **快照**：生成报告时的题干 |
| snap_question_kind / snap_difficulty | 快照 |
| snap_point_name | **快照**：生成报告时的主知识点名称 |
| snap_criteria | **快照**：当时的考察点 / good_criteria / bad_criteria |

> **本表没有「每题一段总结」字段**（决策 27 删除）：逐题评语就是 `evaluations.review`，不重复生成。
>
> **快照的边界（必须严格遵守）**：
> - **快照**的是「依据」—— 题干、考察点、criteria、知识点名。它们会被编辑，且历史报告必须显示**当时**的样子。
> - **不快照**的是「结论」—— 分数、评语读 `evaluations`，`hits` 读 `attempts`（累积快照）。它们是历史事实，本来就不会变。
>
> 为什么必须有：题会被**隐藏 / 删除 / 改挂载**（分步公开、挂载自修复、去重合并都会导致）。不快照的话，历史报告会显示一道已经不存在的题、或一条当时根本没被问过的考察点。

### `sessions`
第二层（题会话）。沿用 v1 的名字与大部分语义。

| 字段 | 说明 |
|---|---|
| id / interview_id / question_id | |
| seq | 本场面试中的第几题 |
| status | active / finished |
| max_rounds | 本道题的追问上限（**编排参数，不再由难度推导** —— ADR-0001） |

> v1 的 `uq_sessions_active`（同用户同题单 active）改为 `(interview_id, seq)` 唯一 + 每用户每场一个 active interview。

### `attempts`
轮次。沿用 v1，但**三处结构性变化**：删掉 `level`（追问阶梯废弃），用 `hits` 取代 `quality` / `completeness`，新增语音输入相关字段。

| 字段 | 说明 |
|---|---|
| id / session_id / round_no | |
| is_followup | |
| **input_mode** | `voice` / `text` —— 本轮是说的还是打的（决策 32：面试页默认语音、可随时切回打字） |
| **stt_text** | **语音识别的原始输出**（含口语停顿与措辞）。仅 `input_mode=voice` 时有值 |
| answer_text / feedback_text | 候选人的话（**最终落库、被判分的那份表述** —— 语音轮即转写文本）/ 面试官的话 |
| **hits** | **本轮对当前题全部考察点的命中状态**（JSON：`criterion_id → 命中状态`），是**累积快照**而非增量 |

> ⚠️ **命中状态是「三值」：命中 / 未命中 / 未涉及**（`CONTEXT.md`「命中状态」是权威定义）。第三值不是可选装饰 —— **掌握度矩阵的分母是「被考过的考察点」**，靠它把本轮没问到的考察点排到分母之外。只有两值时，「本轮没问到」与「答错了」在库里长得一样，`docs/v2范围基线.md`「『没考过』是空格、『考了但没答』是 0%」那条就没有落地依据。
>
> 三值与 `question_point_stats` 的两列计数不冲突：**「未涉及」两条数据线都不计**（既非命中亦非未命中），所以聚合表不需要第三列。
>
> ⚠️ **键是 `criterion_id`（考察点的稳定 id），不是 `seq`** —— `question_point_stats` 必须能用同一个键对上它，否则注销时的「累加进聚合表」没有对照物（见 §6）。

> ⚠️ **为什么 `stt_text` 与 `answer_text` 必须分开存**：
> 语音模式下**转写直接进判分，不设确认环节**（决策 33）—— 同音错别字由 LLM 靠上下文读通（"红黑树"被转写成"红黑书"，句子不成立，模型复述不出来）；两列在多数轮次里内容相同，用户顺手改过才不同：
> - **判分与追问看 `answer_text`** —— 那是最终落库、被判分的那份表述
> - **「表达清晰度」看 `stt_text`** —— 口语停顿、口头禅、重复这些信号只在原始转写里
> 若只存一个，要么丢掉表达信号（用户顺手把"嗯……那个"删了），要么让判分读不到实际提交的表述。
>
> ⚠️ **不保存原始录音**（决策 33 明确）：录音是敏感数据且体积大；转写文本足够。

**删除的 v1 字段：**

| v1 字段 | 为什么删 |
|---|---|
| `level`（L1-L5 深挖层级） | 追问不再按预设阶梯推进（`docs/v1行为规格.md` §3.8 / §3.10 标记为废弃） |
| `quality`（correct/partial/wrong/unsure） | **被 `hits` 取代**（决策 28）：探能力边界需要的是"漏了哪几条"，而 `quality` 只说明"好不好"，粒度配不上目标。两个并存会让"回答好坏"出现两种可能不一致的表示 |
| `completeness`（complete/partial/incomplete） | 同上 —— 它就是"命中了多少条"的粗粒度说法，`hits` 直接给精确答案 |

> ⚠️ **`hits` 为什么必须是「累积快照」而不是「本轮增量」**：
> 它要同时服务三件事 —— ① 追问决策（"此刻漏了什么"）② 掌握度矩阵（"最终答到了什么"）③ 挂载自修复。
> 若是增量，② 就要把整条会话的增量并起来算，而"未命中"这种**缺席**信息在增量语义下无法表达。
> 累积快照则让三者都变成**读最后一行**即可。

> ⚠️ **它逐轮都要产出**，不是整场结束才判定 —— 因为追问本身要靠它决定下一问问什么。这比 ADR-0003 原先只要求"面试进行中判定"更严格。
>
> ⚠️ **它必须能表达「题目问了但用户完全没答」**（该考察点记为未命中），而不是只在用户答到时才有记录 —— 因为「考了但没答」与「没考过」对候选人是两件事（前者是 0%，后者是空格）。这也是掌握度矩阵上「0%」与「空」的区别。

### `evaluations`
取代 v1 的 `judgments`。**这里是题会话级的最终评分**（不是逐轮评分）。

| 字段 | 说明 |
|---|---|
| id / session_id | |
| scores | accuracy / completeness / clarity / depth（四维，继承 4.1） |
| total_score | `.3/.3/.2/.2` 合成（继承 4.2） |
| review | 评语（面试报告"逐题回顾"里的那一段，不重复生成） |
| status | ok / failed（继承 4.4：失败也要落库，不静默） |

> **`hits` 不在本表**（决策 28 移出）：它随轮次累积在 `attempts` 上，本表若要引用则**汇总该会话最后一轮的快照**。它同时供：① 追问决策 ② 掌握度矩阵聚合 ③ 挂载自修复的信号 ④ 薄弱点与前置推荐 ⑤ 面试报告的"该补什么"。v1 的 `weak_tags`、`quality`、`completeness` 三个字段全部被它取代。

> ⚠️ **`clarity` 是四维里唯一一个含义随输入模态变化的维度**（决策 32 的连锁，写判分 prompt 时会撞上）：
> - **打字模式**：clarity = 结构清晰、有条理（测的是组织与排版）
> - **语音模式**：clarity = 表达流畅、少口头禅（测的是说话）
>
> 因此判分 prompt 需要**按 `attempts.input_mode` 给不同的 clarity 评分提示**，且语音模式下应参考 `stt_text`（原始转写）而不是 `answer_text` —— 后者在用户顺手改过之后会丢掉口语特征。是否干脆把 clarity 拆成两个维度，留到写 prompt 时定。

### `jobs`

| 字段 | 说明 |

> ⚠️ **任务函数必须幂等**：超时回退与手动重跑都会导致同一任务跑两遍。有副作用的任务（发通知 / 扣额度）要么不进队列，要么加去重键。

### `question_point_stats`
**新表**。**聚合**质量信号（**它不是匿名数据** —— 见 §9 风险③）。

| 字段 | 说明 |
|---|---|
| question_id / point_id / criterion_id | 复合主键 |
| hit_count / miss_count | 累计计数 |
| updated_at | |

> 无 user_id、无会话 id，只有计数。服务三件事：挂载自修复的信号（"这道题的这条考察点大家普遍答不到"）、难度标定、题库质量分析。
> 注销用户时：先把该用户的 `attempts.hits` 累加进本表，再删掉逐条记录。
>
> ⚠️ **键必须是 `criterion_id`，不是位置**：`attempts.hits` 是 `criterion_id → 命中状态` 的映射，聚合表要用同一个键才能对上。第一版写的是 `criterion_index`（seq 位置），两个后果都是静默的 —— ① 注销聚合没有可用的对照键；② 考察点被删或重排后，历史计数会**指向另一条考察点**。而 ADR-0002 已明说知识点定义会随人审而变，所以这不是假想风险。
>
> ⚠️ **不要称它为"匿名数据"**：当前规模（20 人以内）下，用剩余计数做减法即可反推出被删除用户答了什么。它在用户数约 50 以上后自然失效。在此之前，注销流程的合规依据是「用户要求删除」，**不是**「数据已匿名化」。

## 9. 已知风险

### ① 私有/公共同表（`questions`）的越权风险
`questions` 同时装公共题库与所有人的私有题集，任何一处查询漏了 `owner_user_id` 过滤就是数据泄露。
→ 缓解：所有题目查询**必须经过一个统一入口**（一个查询构造函数），不允许业务代码直接写 `select(Question)`。这条已写成硬规则（`AGENTS.md` §3.5）。

### ② 数据只增不减
实测：一天 20-60KB，一年不到 1GB —— **量级上不是问题**（见 Open-4）。保留此条只为提醒：`attempts` 不设上限，增长取决于用户活跃度，而这是你唯一无法预估的变量。
→ 缓解：`attempts.answer_text` 设长度上限；观测页展示库体积。

### ③ 保留判定 vs 掌握度矩阵互相冲突 → 已解决：拆成两条数据线
这个风险在决策 21（注销）的决定之后才浮现出来：

- 掌握度矩阵是**每个用户自己**的视图，聚合时必然按 `user_id` 过滤
- 而注销时清掉 `user_id` 的判定数据，会**混进聚合结果里被重复计入**（再也无法排除它）
- 更根本的：**矩阵需要的就是「某人 × 知识点」的判定记录，那本身就是个人信息** —— 靠"匿名化判定"喂不出矩阵

**结论：两条独立的数据线，不共用一张表。**

```
线 1  attempts.hits          带 user_id
      服务：掌握度矩阵 / 薄弱点 / 面试报告
      注销时：随用户删除

线 2  question_point_stats  不带 user_id（只有计数）
      服务：挂载自修复信号 / 难度标定 / 题库质量分析
      注销时：先把线 1 的记录累加进来，再删线 1
```

**新增表 `question_point_stats`**（定义见 §6）：只有 `question_id / point_id / criterion_id / hit_count / miss_count`，无任何 user_id 或会话 id。

> ⚠️ **但它不等于匿名。** 在小样本下（当前 20 人以内），用「总数 − 你自己的记录」做减法，就能反推出被删除的人在哪些考察点上答对或答错 —— **泄露的不是身份，是内容**。
>
> 处理方式：**接受它，并写明它**。
> - 实际伤害极低（20 个认识的人，你不会去关注谁答错了什么）
> - 用户数约 50 以上后自然失效（减法反推不出来）
> - **在此之前，注销流程的合规依据是「用户要求删除」，不是「数据已匿名化」** —— 隐私说明里不许把它写成匿名数据

### ④ 报告快照问题 → 已解决：快照依据，不重算结论
报告的**主体与总结都是拼装产物**（ADR-0003；字段见 `interviews.report_body` / `report_summary`），而它拼装的素材**全都是会被编辑的**：知识点定义（你正在审的骨架必然要改）、题目 `good_criteria`、题目本身（会被隐藏 / 删除 / 改挂载）。

后果：报告生成时按当时素材拼装一次，用户下周打开看到的却是改过的素材 —— 会自相矛盾（"评语说我没答到拒绝策略，但考察点列表里根本没这条"），题被隐藏则整块碎掉。

**结论：`report_items` 快照判分依据（见 §5 作答侧）。**

```
快照（依据，会变）：题干 / 考察点 / good·bad criteria / 知识点名
不快照（结论，是历史事实）：分数 / 评语 → 读 evaluations；hits → 读 attempts
```

**一句话原则：历史报告里的「结论」是事实，永不重算；「依据」是引用，必须快照。**
