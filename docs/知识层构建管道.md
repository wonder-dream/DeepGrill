# 知识层构建管道（开工文档）

> 状态：会过期（实现后由离线领域的代码与 prompt 文件替代）｜ 被什么替代：离线领域的代码与 `prompts/`；届时只保留成本模型与验收标准。

> 用途：把 v1 的题目变成**知识地图 + 每题的知识点归属**。这是 v2 写代码后要跑的**第一件事**。
> 它不是 ADR —— 因为可以重跑（几块钱一次），且设计上没有真正被权衡掉的备选。
> 📌 **本文的成本模型与工序参数（批大小、调用次数、耗时、花费）以本文为权威** —— 它们是这道工序自己的参数。**v1 的题量等状态数字见 `docs/v1现状-20260913.md`，本文不复述其权威值。**
> 相关：ADR-0002（知识层是 SQL 里的图）、ADR-0006（离线任务）、ADR-0007（prompt 独立成文件）

---

## 输入

```
第一次：从 v1 的 data/interview.db（只读）全量导入题目进 v2
  路径 / 体积 / SHA256 / 题量等实测值见 `docs/v1现状-20260913.md`（导入前先核对 SHA，确保源没变过）
  导入字段：题干 / type / difficulty / good_criteria / bad_criteria
            + 一份「题目 id → v1 原标签」映射（聚类辅助信号与回查依据）

之后：管道只对着 v2 自己的库跑
```

**导入是唯一一次读 v1 库的操作**（**决策 49**）。之后 v2 库自足 —— 删掉 v1 目录，重建知识层仍然做得到；而且**初始装配与增量维护因此走同一条路径**（都对着 v2 库），不会分叉。

v1 的标签体系本身不进 v2 的产品结构（主题维度 ≠ 能力维度，见 ADR-0002），只作为辅助信号保留在导入映射里。

**排除项**（题 id 见 `docs/v1现状-20260913.md`）：`id 62 / 69`（「请介绍您参与的 RAG 项目…」，来自简历、对任何人都不可答）剔除；`id 2136` 改写为通用题。

## 成本模型（这是可行性的关键）

```
素材体量（估算）：每题 ≈ 180 字（题干 + good + bad）
          **题量按实际导入结果算**（见 docs/v1现状-20260913.md）
          按导入时的实际题量推算：总数 ≈ 54 万字 ≈ 54 万 token

每批 50 题 → 约 61 次调用
  → 输入约 61 万 token + 输出约 18 万 token
  → 成本：几块钱量级
  → 耗时：20 分钟到 1 小时
```

**结论：它不是"跑几小时的离线大任务"，而是一次跑完的小任务 —— 因此可以反复试错。** 这直接决定了它的运行方式：**用命令行手动跑**（能看实时输出、能中断、能 `--dry-run`），而不是进 worker 队列。

## 七个步骤

| # | 步骤 | 调用数 | 产出 | 人审 |
|---|---|---|---|---|
| 1 | 分批提候选知识点 | ~61 | 300-900 个候选（允许跨批重复） | — |
| 2 | 嵌入 + 聚类 | 1 次嵌入 | 若干候选簇 | — |
| 3 | 簇内判断与归并 | 每簇 1 | 知识点清单（名称 + 定义 + 考察点） | — |
| 4 | **★ 人审 ★** | — | 通过 / 否决 / 合并后的确认清单 | ✅ |
| 5 | 分批挂载题目 | ~61 | 每题 → 主知识点 + 关联知识点 | — |
| 6 | 生成前置依赖边 | ~1（分批） | 森林的边（前置依赖） | — |
| 7 | **★ 人审 ★** | — | 边对不对 | ✅ |

**两处人审，审的都是小体积产物**（几百个节点、几十条边），不是全库题目的挂载结果。这是整套设计里最重要的一点 —— 它把人的注意力放在最便宜的位置。

### 为什么第 2、3 步不直接做"一次全局归并"

61 批汇总起来约 3-5 万 token，**现在能塞进一次调用，但题库一长就塞不下**。更麻烦的是**归并是传递的**：A 与 B 相似、B 与 C 相似，若 A 与 C 落在不同批里，它们永远不会被合并。

用嵌入粗筛解决这两点：

```
候选名称算嵌入（几百个向量，几乎零成本）
   → 按向量聚类 → 得到候选簇
   → LLM 逐簇判断：这几条是不是同一个知识点？叫什么？定义是什么？

上限：无（每次只看一个簇）
传递性：聚类算法天然处理（向量空间里它们本就靠近）
可审查性：一个簇一个决定，能看懂"为什么把这三条合成一个"
```

## 两个阶段

| 阶段 | 输入 | 频次 | 挂不上时 |
|---|---|---|---|
| **首次装配** | 种子题全量（题量见 `docs/v1现状-20260913.md`） | 一次性 | 不可能发生（就是从它们提炼的知识点） |
| **增量** | 每天新生成 / 晋升的题 | 长期 | 进**待定池** |

**增量期绝不允许自动新建知识点** —— 那等于让 LLM 悄悄改知识地图，而 ADR-0002 已定：骨架的判定权在人手上。

正确做法：**挂不上的题进「待定池」**，连同它提议的新知识点一起等人处理。待定池不需要 UI，它是首页上的一个数字（「还有 12 道题挂不上，其中 3 个新知识点待确认」）。

---

## 人审怎么做

- **首次装配**：一次性最小审核页 —— 一个页面，列出候选簇及其成员，逐条「通过 / 否决 / 合并」，批量提交。
  它比 v1 的 `reviewer.*` 简单一个量级：**不需要权限、分页、搜索**（几百条一次加载完）。
- **增量**：待定池积压到一定数量时再处理。
- 两者共用同一套「提案 → 审」的逻辑。

## 每一步的验收标准

| 步骤 | 怎么知道这步对了 |
|---|---|
| 1 提候选 | 抽查 3 个批次：候选里有没有把「一道题的主题」当成知识点？（那是标签，不是知识点） |
| 2-3 归并 | 抽查 10 个簇：簇内成员是不是**真的在考同一件事**？有没有把「相关」误判成「相同」？ |
| 4 人审 | —— |
| 5 挂载 | **结构性检验（可自动）**：是否存在「一个知识点下 0 道题」的节点？是否存在「一道题没有任何知识点」？（后者应被外键禁止） |
| 6 前置边 | **优先审「只有一边信号指向」的那些边**（两个信号都指向的可信度高）。另外自动检查：有没有成环？深度是否都 ≤2？ |
| 7 人审 | —— |
| **上线后** | **行为检验**：挂载自修复的信号 —— 有没有题长期无人命中它主知识点的考察点 |

## 第 6 步的可靠性：全链最弱的一环（**决策 48**）

必须承认：**从知识点名字推前置边，属于开放集关系推断** —— 工具只有两个名字，没有内容依据，LLM 基本在猜。通用 RE 至今不可靠，这一步不能例外。

所以**只保留两类有依据的边**：

| 来源 | 依据 | 可靠性 |
|---|---|---|
| **第 5 步挂载时采集的「涉及概念」** | **真实题目内容**（"「volatile 底层靠内存屏障」→ 涉及内存屏障但未考察"） | 较高 |
| **领域内推断的边** | 学科结构 —— 限定同领域、限深 ≤2 层、要求 LLM **给出理由**、强制无环 | 中（需人审） |

**两处采集的边合并后直接对账**：两边都指向的同一条 → 可信度高；只有一边指向的 → 单独列出来供优先审。

**为什么限深 ≤2 层**：这不是整洁性设计，是**对幻觉的防御**。允许无限深度时 LLM 会推出一条 10 层的链，而每一层都可能是编的。限制在 2 层内，错误的影响范围可控 —— 而复习推荐只需要 1-2 跳（"先补 JMM，再回来做 volatile"），更深的路径对产品没有额外价值。

**边的质量会随数据改善**：等有真实用户后，可以从答题数据挖可靠信号 —— 「会知识点 A 的人是否大概率会 B」。那才是真正有依据的关系抽取。**初期不追求森林的深度，只追求"不把用户带错方向"。**

## 未定

1. **批大小 50 是不是最优？** —— 没验证过。批太小则跨批重复多，批太大则单次输出质量下降。这是第一个该试的参数。
2. **候选知识点的定义写到多细？** —— 第 1 步只提名称，还是连考察点一起提？倾向只提名称 + 一句释义，把考察点的生成放到第 3 步（那时才有全局视野）。
3. **第 5 步的「涉及概念」会不会拉低挂载质量？** —— 让一次调用同时干两件事（挂载 + 采集涉及概念）可能让输出变长、质量下降。需实测；若下降，拆成两次调用。
