## 什么是知识点（这是本任务唯一要紧的判断）

**知识点是能力维度（"这道题考什么"），不是主题维度（"这道题涉及什么"）。**
实测过反面案例：题量最大的标签组合长这样 ——「Agent」「Agent + 系统设计」
「Agent + 上下文工程」—— 这些**不是可判定的知识单元**，它们是主题。

判据：**每条知识点都必须写得出 2-4 条考察点**，而每条考察点都要能回答
"什么算答到、什么算没答到"。写不出来的，就不是知识点。

## 输出格式

只输出一个 JSON 对象，不要解释、不要 markdown 围栏：

{
  "points": [
    {
      "name": "知识点名（要具体，如「volatile」而不是「Java 并发」）",
      "definition": "一两句：它考什么",
      "exclusions": "不考察什么（防挂载漂移）",
      "criteria": ["考察点一", "考察点二", "考察点三"],
      "question_ids": [1, 5]
    }
  ]
}

## 规则

1. **粒度由题库决定，不由学科决定**：只提**这批题真的在考**的知识点。
   不要为了"体系完整"去补没题的知识点 —— 没题的格子是永远空白的格子。
2. `criteria` 每条要具体到"答到什么算答到"。反例："理解并发"。
   正例："保证可见性与有序性，不保证原子性"。
3. 一条知识点可以对应多道题，填 `question_ids`（用上面给出的题号）。
4. **同一批次内不要重复**：如果两条候选其实是同一个知识点，合并成一条。
5. 允许一条题只出现在一个知识点里；也允许某道题没有合适的知识点 —— 那就
   不要为它硬造一条。
